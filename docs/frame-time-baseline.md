# Базлайн кадрового времени

Обновлять при каждом изменении, которое трогает кадровый путь.

## Как снять

```
build/release/apps/test_world_grid/test_world_grid.exe --bench=parked     --bench-frames=600  --bench-out=bench_parked.txt
build/release/apps/test_world_grid/test_world_grid.exe --bench=flythrough --bench-frames=1500 --bench-out=bench_flythrough.txt
```

`--bench=<parked|flythrough>` включает режим и выставляет умолчания
(2000 замерных кадров, 200 на прогрев, фиксированный шаг 1/60 с);
`--bench-frames`, `--bench-warmup`, `--bench-out` их переопределяют.

Замер стартует не сразу: движок ждёт, пока сцена доложит о готовности
(`app::is_bench_ready`), и только потом начинает отсчёт прогрева. В
`test_world_grid` готовность — это ноль незагруженных колонок и ноль
незавершённых мешей, то есть начальная прогрузка целиком за кадром замера.

Камера ведётся по номеру кадра, а не по времени: полёт по часам давал бы разную
траекторию на разных машинах. Мир получает фиксированный шаг, чтобы симуляция не
плыла вслед за той самой частотой кадров, которую и меряем.

## Условия

| | |
|---|---|
| GPU | NVIDIA GeForce RTX 3070 |
| Сборка | Release, MSVC |
| Режим представления | mailbox (**не** vsync-ограничен) |
| Кадров в полёте | 2 |
| Сцена | `test_world_grid`, сид 42, `voxel_scale = 8` |

**Прогонять оптимизации на всех четырёх сценах.** `parked` и `flythrough` обе
смотрят с высоты и обе ведут камеру плавно; на них не видно ни цены поворота, ни
цены непрерывного стриминга. Добавлены `spin` (камера стоит и вращается) и
`advance` (камера идёт вперёд без остановки) — первая же их пара нашла просадку,
которой не было ни в одной из старых.

```
test_world_grid.exe --bench=parked|spin|advance|flythrough
```

Режим представления в отчёте не для красоты: `choose_swap_present_mode`
(`renderer.cpp:1718-1727`) берёт mailbox если он есть, иначе fifo. На машине с
fifo замер упрётся в частоту монитора и покажет ровные 16,6 мс — числа ниже с
таким прогоном несравнимы.

### До и после `deletion_queue`

Числа `flythrough` на 1500 кадрах, снятые до и после снятия дренажа очереди из
пути расширения буферов:

| | до | после | |
|---|---|---|---|
| frame p50 | 1.829 | **1.656** | −9,5 % |
| frame p95 | 3.147 | **2.244** | −28,7 % |
| frame p99 | 3.439 | **2.598** | −24,5 % |
| frame max | 3.910 | **3.088** | −21,0 % |
| buffer_pool_update p50 | 0.007 | 0.015 | +0.008 |

Выигрыш оказался шире ожидаемого: движения ждали в хвостах, а p50 сдвинулся
почти на столько же, сколько p99. Объяснение в том, что́ именно
убрали: `queue.waitIdle()` не просто задерживал кадр, в котором случилось
расширение, — он опустошал весь конвейер, и следующие кадры начинали с пустого
GPU. Поэтому потери размазывались по кадрам, где никакого расширения не было.

`buffer_pool_update` при этом вырос: CPU-работа по записи копий никуда не
делась и теперь честно попадает в эту стадию, тогда как раньше её основная
цена уходила в простой GPU и учитывалась как `begin_frame`.

## GPU-время (таймстемпы)

Снято 15 августа 2026 г., после `gpu_timer` (задача P0.1 из
`optimization-plan.md`). Все стадии выше меряют **запись команд**, эти —
**исполнение**. Пул запросов на кадр в полёте, результаты читаются в
`begin_frame` за тот же фенс, что уже дождались.

|---|---|---|---|---|
| **gpu_frame** | **1.574** | **2.144** | **1.400** | **2.058** |
| gpu_buffer_upload | 0.000 | 0.000 | 0.000 | 0.106 |
| gpu_compute_cull | 0.127 | 0.139 | 0.124 | 0.135 |
| gpu_shadow_pass | 0.706 | 0.715 | 0.656 | 0.740 |
| gpu_world_pass | 0.740 | 1.312 | 0.601 | 1.236 |
| gpu_world_geometry | 0.709 | 1.278 | 0.565 | 1.197 |
| gpu_world_debug | 0.001 | 0.002 | 0.001 | 0.002 |
| gpu_world_imgui | 0.009 | 0.010 | 0.010 | 0.012 |

`parked` — 600 кадров, `flythrough` — 1500. Это состояние **до** расписания
каскадов; актуальные числа — в следующем разделе.

**Метки сходятся с двух сторон.** Сумма подстадий `parked`
(0.127 + 0.706 + 0.740 = 1.573) равна `gpu_frame` (1.574), а сам `gpu_frame`
(1.574) — это почти в точности `begin_frame` (1.525), то есть время, которое CPU
простаивает в `waitForFences`. Два независимых подтверждения того, что метки
стоят там, где заявлено.

**Тени — 45 % кадра GPU.** 0.706 мс из 1.574 уходят в четыре каскада 2048² D32,
которые перерисовываются каждый кадр. Столько же (0.709) стоит основная
геометрия, при том что теневой проход пишет только глубину.

**`gpu_buffer_upload` реагирует на стриминг:** ноль в `parked`, 0.106 мс на p99
в `flythrough`. Стадия ловит ровно ту работу, ради которой заведена.

**Воспроизводимость** двух прогонов `parked`: `gpu_frame` 1.574 против 1.568
(0,4 %), `gpu_shadow_pass` 0.706 против 0.705 (0,1 %).

**Оверхед инструмента** в пределах шума: `frame` p50 1.807 и 1.740 против 1.827
в прогонах до таймстемпов.

Стадии вложены (`gpu_world_geometry` внутри `gpu_world_pass`) и GPU их
перекрывает, поэтому части не обязаны складываться в целое — сравнивать имеет
смысл каждую с самой собой до и после правки.

## После расписания теневых каскадов (P6.1)

Медиана по трём прогонам на сцену. Каскад перерисовывается, только когда камера
вышла за запас покрытия, повернулся свет или изменилась геометрия внутри него;
не больше двух каскадов за кадр, пока запас позволяет ждать.

| | до | после | |
|---|---|---|---|
| **parked** frame p50 | 1.807 | **1.016** | −44 % |
| parked gpu_frame p50 | 1.574 | **0.860** | −45 % |
| parked gpu_shadow_pass p50 | 0.706 | **0.000** | каскады не перерисовываются |
| **flythrough** frame p50 | 1.656 | **1.147** | −31 % |
| flythrough frame p99 | 2.449 | **2.138** | −13 % |
| flythrough gpu_frame p50 | 1.400 | **0.909** | −35 % |
| flythrough gpu_shadow_pass p50 | 0.656 | **0.149** | −77 % |
| flythrough gpu_shadow_pass p99 | 0.740 | **0.741** | без изменений |

Цена каждого каскада по отдельности (`flythrough`, кадры, где каскад
перерисовывался): 0.15 / 0.16 / 0.18 / 0.27 мс. Дальний стоит вдвое дороже
ближнего — он покрывает больше чанков.

**Хвост пришлось чинить отдельно.** Первая версия обновляла каскад ровно тогда,
когда кончался запас, и p99 теневого прохода вырос с 0.740 до 1.23: кадры без
работы чередовались с кадрами, где перерисовывались все четыре. Помог зазор
между «пора обновить» (0.15 радиуса) и «покрытие кончилось» (0.18) плюс лимит в
два каскада на кадр — в этот зазор каскад может подождать более спокойного
кадра. Промежуточная попытка с зазором втрое шире (порог 0.05) сделала хуже:
она не разносила работу, а добавляла её, и медиана перерисованных каскадов
выросла с 1 до 2.

**Что за это заплачено:** карта каждого каскада покрывает на 18 % больший
радиус при том же разрешении 2048², то есть тени примерно на 15 % грубее.
Артефактов быть не должно по построению — сумма дрейфа (0.18 R) и требуемого
радиуса (R) равна радиусу карты (1.18 R), — но проверено это арифметикой, а не
глазами: скриншот-тестов в проекте нет.

## После честного index_count (P1.1)

Indirect-команда рисовала полную ёмкость класса буфера, а хвост занулялся через
staging. Теперь команда несёт реальную длину меша, зануления нет.

| | до | после | |
|---|---|---|---|
| **parked** frame p50 | 1.016 | **0.988** | −3 % |
| parked gpu_frame p50 | 0.860 | **0.808** | −6 % |
| parked gpu_world_pass p50 | 0.738 | **0.680** | −8 % |
| **flythrough** gpu_frame p50 | 0.909 | **0.810** | −11 % |
| flythrough gpu_world_pass p50 | 0.601 | **0.513** | −15 % |
| flythrough gpu_shadow_pass p50 | 0.149 | **0.127** | −15 % |

Меньше, чем можно было ожидать от «25–35 % лишних индексов»: паддинг состоял из
нулей, то есть из вырожденных треугольников на одной и той же вершине. Она
попадает в кэш после первого же обращения, вершинный шейдер за неё платит один
раз, и остаётся только выборка индексов и отбраковка в primitive setup. Это и
есть те 8–15 %.

`buffer_pool_update` (CPU) вырос с 0.005 до 0.024 мс p50. Два кандидата, и
разделить их нечем: `write_mesh` теперь обходит инстансы буфера, чтобы
переписать команды ремешенного меша, а бюджет staging перестал считать паддинг
и пропускает за кадр больше мешей. Обход растёт как «инстансы × ремеши за
кадр», и если станет заметен, лечится обратным индексом меш → инстансы.

## После MSAA, дальности отсечения и reversed-Z (P1.9 + P1.2 + P2.1)

Три правки в одну область — проекция и render pass основного прохода. Замерены
по очереди, чтобы вклад был виден отдельно (`parked`, `gpu_world_pass`, медиана
трёх прогонов):

| Шаг | gpu_world_pass | |
|---|---|---|
| исходно | 0.680 | |
| **MSAA выключен** | **0.632** | −7 % |
| дальность = дальность тумана | 0.623 | −1.4 % |
| reversed-Z | 0.634 | +1.7 %, в пределах шума |

**MSAA (P1.9).** Медиана −7 %, но по хвостам гораздо больше: `gpu_frame` p95
шёл 1.03–1.10, стал 0.759–0.765. Разброс кадра почти исчез — сглаживание стоило
не столько среднего времени, сколько его стабильности. Освободилось порядка
30 МБ VRAM под MSAA-таргеты (1280×720). Картинка теперь алиасная — это принятое
решение, не регрессия.

**Дальность отсечения (P1.2) дала 1.4 % вместо ожидавшихся 19 %.** Оценка в
плане считала долю площади кольца между туманом (4608) и радиусом загрузки
(5120) и была неверной: камера смотрит почти горизонтально, земля уходит за
горизонт на первой паре тысяч единиц, и геометрии за туманом в кадре почти нет.
Правка остаётся верной по смыслу — рисовать залитое туманом незачем, — но её
цена в этой сцене близка к нулю. Чанки за туманом при этом по-прежнему грузятся
и мешатся: `view_distance` не тронут, это отдельный расход памяти и CPU.

**Reversed-Z (P2.1) перф-нейтрален,** как и задумано: это правка точности.
Первая версия с `eGreaterOrEqual` стоила ~4 % — исходный `eLess` строгий, и
ослабление теста пропускало фрагменты равной глубины; с `eGreater` разница
укладывается в шум. Корректность матрицы закрыта тестом
(`math perspective_matrix_reversed`): near → 1, far → 0, глубина убывает с
расстоянием.

## CPU-сторона: мешинг и генерация (P1.3–P1.8)

Сначала пришлось завести метрики: мешинг и генерация колонок идут на своих
воркерах и в кадровые перцентили не попадают вообще. Обе сводятся по единице
работы, а не по кадру, и печатаются отдельными блоками в конце отчёта.

**Первое, что показал замер:** мешинг чанка стоит **5.7 мс** (p50), при цели
плана в 200 мкс — в 28 раз больше. Генерация колонки — **15.4 мс**. Очередь
колонок при облёте стояла на 52–74 задачах.

| на чанк mean | 5157 | **4841** | −6 % |

| пик очереди | 118 | 72 | |

### Генерация колонки (P1.5 + P1.6)

Замерено четырьмя сборками, чтобы разделить вклад:

| Кэш высот | Запись без мьютекса | p50 колонки |
|---|---|---|

(1119 против 1167), а квадов на чанк — больше (7940 против 7270).

## Фаза 4: тест мешера и битовые границы (P0.7 + P4.1)

`gfx_tests` — новый таргет, линкует `vw_gfx` и не открывает устройство.
Дифф-тест сверяет greedy-мешер с по-воксельным: квады раскладываются обратно на
единичные грани, и два мешера обязаны выдать одно и то же множество на пустой
модели, одиночном вокселе, вокселе в углу, сплошном кубе, шахматке, двух
материалах и случайной заливке. Плюс golden-хеш на регрессию и отдельный тест
на стык: у соседа берётся грань, и сторона +X должна исчезнуть целиком, не
задев остальные пять.

`boundary_slice` (`std::vector<bool>` плюс глубокая копия при каждой передаче
соседу, двенадцать раз на чанк) заменён на `face_occupancy` — 64 слова по 64
бита, POD, копия в 512 байт без аллокации.

**И тут вскрылась ошибка в уже принятом P1.6.** Я добавил `set_voxel_raw` как
обёртку, но не убрал `increment_generation_()` из тела: мьютекс никуда не делся,
а замер сравнивал один захват с двумя. Настоящий результат сильно больше
заявленного тогда:

| Шаг | p50 колонки | |
|---|---|---|
| было записано после P1.5+P1.6 | 5807 мкс | |
| битовые границы (P4.1) | 5188 | −11 % |
| **мьютекс действительно снят** | **863** | **−83 %** |

От исходных 15357 мкс это **в 17.8 раза**. Мешинг не изменился (5191 мкс) —
P4.1 меняет только источник граничных бит, не сам обход.

### P4.3: маски граней битами

Маска слоя больше не заполняется по ячейке. Видимость целой строки из 64 ячеек —
одно `cur & ~next` по occupancy, пустой слой виден без единого обращения к
маске, и записываются только те ячейки, где грань есть (обычно единицы
процентов). Материал и AO пока считаются по-старому — это P4.4.

| | до | после | |
|---|---|---|---|
| мешинг чанка p50 | 5295 мкс | **2807** | −47 % |
| p99 | 7407 | **3990** | −46 % |
| пик очереди мешинга | 133 | 133 | |

Заодно очередь колонок стала успевать: за те же 1500 кадров обрабатывается 1890
чанков вместо 1803 при том же числе квадов на чанк (7940).

Раскладка occupancy подобрана так, что для ±Y и ±Z строка соседа — это соседнее
слово того же массива, а для ±X — слово второй ориентации. Единственное место,
где биты собираются по одному, — граничная плоскость соседа для ±X: её
раскладка y-мажорная, и это один слой из шестидесяти четырёх.

Тесты пришлось расширить: все прежние случаи были на моделях 16³ и 32³, а
битовый путь включается только на 64³. Добавлены три полноразмерных случая
(рельеф, разреженный шум, сплошной куб), и тест на стык переведён на 64³ — он
единственный проверяет сбор граничных бит для ±X.

### P4.4: ambient occlusion из тех же бит

Восемь семплов вокруг ячейки читались из страничного объёма — восемь
`is_solid_at` на каждую видимую грань, а для верхней ещё восемь на подсветку.
Теперь это восемь битов из трёх соседних строк occupancy: строки сдвигаются
один раз на всю строку ячеек, и каждый семпл становится битом `u` какой-то из
готовых масок.

| | до | после | |
|---|---|---|---|
| мешинг чанка p50 | 2807 мкс | **2077** | −26 % |
| p99 | 3990 | **2840** | −29 % |

Ячейки на краю слоя (`u` или `v` равны 0 или 63) и слои, чья лицевая плоскость
лежит вне чанка, идут прежним скалярным путём: их семплы уходят к соседу, и
только скалярный путь умеет об этом спросить. Это примерно 6 % ячеек и два слоя
из шестидесяти четырёх.

**Эквивалентность доказана, а не предположена.** Golden-хеш стоял на модели 32³,
где битовый путь не включается вовсе, — то есть AO он не покрывал. Добавлен
второй эталон на 64³, и его значение снято дважды: с битовым AO и с
принудительно отключённой occupancy. Оба раза `419103052605503707` при 29218
квадах, то есть меш совпадает бит в бит, включая упакованные значения углов.

### P4.5: слияние по битам

`merge_and_emit_rects` линейно сканировал все 4096 ячеек в поисках непустых,
расширял прямоугольник поэлементным сравнением трёхбайтовых ключей и затем
поячеечно зачищал занятую область. Всё это теперь идёт по битам видимости:
начало рана — `countr_zero`, прямоугольник гасится одним `and-not` на строку, а
маска нужна только чтобы сравнить ключи ячеек, про которые уже известно, что они
установлены. Зачистка маски исчезла совсем — читается только то, что записано в
этом слое.

Заодно исправлена раскладка: индекс был `u * height + v`, то есть расширение
рана по `u` шагало через 192 байта. Теперь `v * width + u`.

| | до | после | |
|---|---|---|---|
| мешинг чанка p50 | 2077 мкс | **739** | −64 % |
| p99 | 2840 | **1297** | −54 % |

## Глубокий мир и пещеры

Мир перестал быть скорлупой: `depth_below_surface = 128` вокселей вместо
`shell_depth = 8`, а внутри вырезаны пещеры — два ridged-поля 3D-шума дают
тоннели там, где сходятся оба гребня, плюс поле каверн сверху. Бедрок и слои
у самой поверхности не режутся.

Числа не сравнимы с прежними напрямую: это другой мир. Сцена `parked`,
`view_distance = 20`:

| | было (скорлупа) | стало (глубокий мир) |
|---|---|---|
| чанков на колонку | 1.16 | **3.14** |
| чанков всего | 1119 | **5272** |
| генерация колонки p50 | 863 мкс | **~35 000** |
| мешинг чанка p50 | 739 мкс | **790** |
| frame p50 | 0.91 мс | **2.60** |

**Пул страниц пришлось чинить первым.** Первый же прогон падал молча: страница
остаётся `sparse` навсегда, даже когда все её воксели — один и тот же камень, и
глубокий мир упирался в 20-битный `pool_index` (1 048 576 страниц). Теперь
`page_pool` при исчерпании говорит об этом вслух, а `model::compact_pages()`
сворачивает однородные страницы обратно в `uniform`/`empty` после заливки чанка.
Без этого глубокий мир не помещается в адресуемый пул в принципе.

**Про решётку для шума.** Шум пещер считается не на каждый воксель, а на сетке с
шагом 4 (17³ узлов на поле) с трилинейной интерполяцией. Я сначала откатил её,
посмотрев только на генерацию, и это была ошибка — сравнивать надо было целиком:

| | генерация | мешинг | frame | квадов |
|---|---|---|---|---|
| шум на каждый воксель | 33.9 мс | 1211 мкс | 4.29 мс | 120 М |
| решётка + интерполяция | ~35 мс | **790** | **2.60** | **60 М** |

Генерация та же, но интерполяция сглаживает мелкую рябь, которую мешер иначе
превращает в квады: геометрии вдвое меньше и кадр в 1.6 раза быстрее.

Генерация колонки в 35 мс — это дорого (было 0.86 мс на скорлупе) и остаётся
кандидатом на оптимизацию: при четырёх воркерах прогрузка 1681 колонки занимает
около пятнадцати секунд.

## Пещеры как сеть тоннелей

Пещеры из шума заменены на тоннели по рёбрам решётки: узел на ячейку, смещённый
от центра, рёбра к соседям, вдоль ребра вырезается капсула. Требование было
«тоннели, по которым ходит персонаж, соединённые между собой», и мерить пришлось
именно это — `tests/world/caves.test.cpp` считает долю воздуха, где помещается
тело 2×4×2, и связность **проходимого** пространства (не воздуха вообще).

Метрика переписывалась трижды, и каждый раз это меняло вывод:

| что мерили | что показало |
|---|---|
| воздух под потолком | 23 % «пещер» — считалась пустота под дном мира |
| воздух между камнем сверху и снизу | 0.7–5.8 %, осмысленно |
| связность всего воздуха | завышена: щели соединяют то, где персонаж не пройдёт |
| связность проходимого | 0.15 — сеть, по которой нельзя пройти |

Шум перебирался в том же порядке. Порог `|n| < w` даёт ширину, обратную
градиенту: залы в одном месте и щели в другом. Расстояние до изоповерхности
(`|n|` делить на длину градиента) выравнивает калибр, а расстояние до линии
пересечения двух поверхностей с поправкой на угол между нормалями убирает клинья
там, где поверхности сходятся полого. Всё это не спасло связность: пересечение
двух изоповерхностей — набор замкнутых петель, а сходятся они лишь там, где три
поля обращаются в ноль одновременно. На регионе 192 вокселя оставалось 17–30
несвязанных кусков. У решётки связность — свойство графа.

Размер региона оказался важнее параметров: тоннель длиной с регион обрезается
его краем, и одна и та же настройка даёт 0.5 на трёх колонках, 0.84 на четырёх и
0.94 на пяти. Ранние замеры на 2×2 показывали 0.82 и были артефактом.

**Реже и толще дешевле.** Площадь поверхности растёт как длина сети на радиус, а
объём пустоты — как радиус в квадрате. При равном объёме редкая решётка с
широкими ходами стоит вдвое меньше геометрии и удобнее для ходьбы:

| шаг / радиус | воздух | проходимо | связность | граней на 1000 вокселей |
|---|---|---|---|---|
| 32 / 3.5 | 5.5 % | 0.39 | 0.87 | 44 |
| 48 / 4.5 | 5.0 % | 0.49 | 0.95 | 33 |
| **64 / 5.0** | **3.5 %** | **0.52** | **0.95** | **21** |
| 96 / 6.0 | 2.3 % | 0.58 | 0.85 | 12 |

Шаг 32 не просто дороже — на нём приложение падало с
`ErrorOutOfDeviceMemory`. Шаг 96 дешевле принятого, но ход шириной 12 вокселей —
это уже зал, а не тоннель. Середина ребра сдвинута хешем, иначе коридоры идут
по прямой на всю длину пролёта; это ~10 % геометрии сверху.

Сцена `parked`, `view_distance = 20`, медиана трёх прогонов:

| | шум (глубокий мир) | тоннели |
|---|---|---|
| frame p50 | 2.60 мс | **4.66** |
| квадов | 60 М | **113 М** |
| мешинг чанка p50 | 790 мкс | **823** |
| генерация колонки p50 | ~35 000 мкс | **6 900** |

Генерация подешевела в пять раз: капсулы касаются лишь нескольких процентов
объёма, а прежние поля считали четыре трилинейных интерполяции на каждый воксель
мира. Кадр при этом вырос почти вдвое — ступенчатая поверхность наклонного
цилиндра сливается в квады хуже, чем сглаженные интерполяцией полости. Это и
есть цена настоящих пещер; геометрия остаётся кандидатом на оптимизацию.

## Пещеры как отдельные системы

Сеть тоннелей заменена на разрозненные системы: на регион 144 вокселя приходится
одна попытка (шанс 0.7), система — три-восемь камер разного радиуса, нанизанных
цепочкой, часть систем имеет наклонный выход на поверхность. Требование было
«проходимые, но не тоннели одного калибра, и не связанные в подземелье»:
связной подземный мир будут делать данжи из комнат, а пещеры — это вид и место
под базовую руду.

Метрики пришлось перевернуть: раньше проверялась связность, теперь — её
отсутствие. Замер на регионе 5×5 колонок в четырёх местах карты:

| участок | воздух | проходимо | просторно | систем | крупнейшая | размах | с неба | граней/квокс |
|---|---|---|---|---|---|---|---|---|
| 0,0 | 0.44 % | 0.50 | 0.21 | 10 | 0.24 | 3× | 0.26 | 3.0 |
| 16,8 | 0.55 % | 0.58 | 0.28 | 5 | 0.56 | 4× | 0.82 | 3.1 |
| 40,24 | 0.20 % | 0.47 | 0.15 | 6 | 0.47 | 5× | 0.54 | 1.4 |
| 64,64 | 0.30 % | 0.41 | 0.13 | 7 | 0.34 | 3× | 0.45 | 2.4 |

«Крупнейшая» — доля проходимого объёма в самой большой системе: раньше это было
0.95 (единое подземелье), теперь 0.24–0.56. «Размах» — отношение самой большой
системы к медианной, то есть насколько они разные. «С неба» — доля подземного
воздуха, до которого доходит флуд-филл сверху; у тоннелей она была ровно 0.

Проверено и обратное: с `cave_entrance_chance = 0` доля «с неба» падает в ноль,
то есть входы делает именно этот параметр, а не что-то ещё.

Сцена `parked`, медиана двух прогонов:

| | тоннели | системы камер |
|---|---|---|
| frame p50 | 3.80 мс | **2.39** |
| квадов | 113 М | **59.5 М** |
| мешинг чанка p50 | 823 мкс | **662** |
| генерация колонки p50 | 6 900 мкс | **4 200** |

Пещер стало меньше по объёму (0.2–0.55 % против 3.5 %), и это видно на всём:
геометрии вдвое меньше, чем у тоннелей, а кадр вернулся к уровню мира вообще без
настоящих пещер. Поверхность граней — 1.4–3.1 на тысячу вокселей против 20.

## P5.1: каллинг по связности — не работает на этом мире

Механизм построен целиком: связность чанка считается при мешинге по occupancy,
обход идёт от чанка камеры, результат — флаг на инстанс, который `cull.comp`
проверяет перед фрустумом. Он **выключен по умолчанию**, потому что на нашем
мире не скрывает ничего.

Причина не в реализации, и это стоило нескольких итераций. Порядок был такой:

| что померили | что вышло |
|---|---|
| воксельный флудфилл от неба | подземного воздуха достижимо **0 %** — скрывать есть что |
| связность парами граней (15 бит), чанк 64 | 0 % скрыто |
| то же, но карманы вместо пар граней | 0 % скрыто |
| карманы, ячейки 32, регион 8 колонок | **66 % скрыто** |
| то же, регион 16 колонок | 0 % скрыто |
| карманы, ячейки 16, регион 16 колонок | **63 % скрыто** |
| ячейки 32, полный мир (41 колонка) | 0 % скрыто |

**Три ошибки по дороге, каждая давала ровно 0 %.** Пары граней не различают, что
небо над склоном и тоннель под ним касаются одной грани в разных местах —
поэтому связность описывается карманами (компонентами пустоты) с масками
открытых блоков на гранях. Незагруженный чанк считался воздухом, и тоннель,
уходящий за край загруженного мира, уводил обход под всё и возвращал с другой
стороны — теперь пустая ячейка проходима, только если она выше своей колонки.
Камере открывались все карманы её ячейки, включая тоннель под ногами.

**Но главная причина осталась.** Сеть тоннелей связна на 95 %, поэтому одна
ложная связь где угодно открывает её целиком. Точность, которой хватает, растёт
с площадью: 32 вокселя хватало на 8 колонок и не хватило на 16, 16 вокселей
хватает на 16 колонок. Полный мир — 41 колонка; сетка, которая его вытянет,
означает 550 тысяч ячеек обхода на кадр.

Стоимость при включении, сцена `parked`: обход 26 мс на кадр при ячейке 32.
Выключенный обход стоит 0.028 мс (только запись флагов) и кадр остаётся
прежним — 3.80 мс p50 против 3.42 мс `gpu_world_geometry`.

Вывод: для того мира правильный инструмент — P5.2 (HZB). Он работает по буферу
глубины и не приближает видимость, поэтому не ломается от одной щели.

**Приписка после смены генератора.** Причина провала — связность сети, а её
больше нет: пещеры теперь разрозненные системы, крупнейшая держит четверть
проходимого объёма. Обход по ним не должен растекаться, так что P5.1 стоит
перемерить, прежде чем считать его закрытым. Правда, и выигрывать стало нечего:
подземной геометрии осталось 1.4–3.1 граней на тысячу вокселей вместо 20.

## Глубокий мир: тысяча вокселей, откат до 256

Мир стоит на фиксированном дне вместо «128 под поверхностью». Сначала дно было
на −960, потом поднято до **−192**: тысяча вокселей — это пять чанков сплошного
камня на колонку, на которые движок пока не умеет не тратиться. Замеры ниже
сняты на −960, и они остаются в силе как ответ на вопрос «во что обходится
глубина сама по себе».

При дне −960 — 16.2 чанка на колонку против 3.14. Заливка идёт постранично —
страница 8³, целиком лежащая ниже камня и внутри одного слоя породы, пишется
одной записью `page_entry`, а по вокселю проходится только полоса, где грунт
действительно меняется.

Чтобы отделить цену глубины от остальных правок, тот же код замерен с дном на
−64 — столько же чанков на колонку, сколько было раньше:

| | дно −64 | дно −960 | |
|---|---|---|---|
| чанков | 3 637 | 27 171 | ×7.5 |
| frame p50 | 2.051 мс | 2.285 | +0.23 |
| gpu_world_geometry p50 | 1.615 | 1.652 | +0.04 |
| страниц пула | 358 954 | 360 568 | **+1 614** |
| генерация колонки p50 | 1 562 мкс | 2 336 | +50 % |
| мешинг, заданий | 11 946 | 104 724 | ×8.8 |
| мешинг, всего | 10.6 с | 65.9 с | ×6.2 |
| квадов | 45.6 М | 47.3 М | +4 % |

**Памяти глубина не стоит.** 23.5 тысячи новых чанков добавили 1 614 страниц —
0.07 страницы на чанк. Без постраничной заливки каждый из них занял бы 512
страниц: 13.9 млн при адресуемом потолке в 1 048 576, то есть глубокий мир не
поместился бы в пул в тринадцать раз. Занятые 34 % — это приповерхностная
полоса, она была там и на мелком мире.

**Кадру глубина стоит 0.23 мс**, и это не геометрия (+0.04), а
`buffer_pool_update`: 0.021 → 0.239 мс на обходе 27 тысяч инстансов вместо 3.6
тысяч.

**Настоящая цена глубины — мешинг**: 55 лишних секунд рабочего времени на чанки,
которые дают 1.7 М квадов из 47. Меши сплошного камня строятся ради того, чтобы
оказаться пустыми. Это содержание следующей фазы.

**Генерация колонки при этом быстрее, чем была до углубления**: 2 336 мкс против
4 200 на мире в восемь раз мельче. Сложились постраничная заливка, снятый двойной
счёт (`sample_column_` вызывал `continent_at` поверх того, что уже посчитал
`height_at`) и ранний выход из `carve_caves_` для чанков, до которых пещеры не
достают.

### Память и спайки, из-за которых глубина откатилась

Отчёт бенчмарка теперь печатает занятость пула страниц и пик RAM/VRAM: без этого
о памяти можно было только гадать. Сцена `flythrough`, тот же код на двух
глубинах:

| | дно −960 | дно −192 |
|---|---|---|
| колонок / чанков | 965 / 15 635 | 1 697 / 7 123 |
| RAM пик | **1 192 МБ** | **581** |
| VRAM | 539 МБ | 533 |
| страниц пула | 95 334 (47 МБ) | 94 774 (47 МБ) |
| frame p50 | 1.673 мс | 1.212 |
| frame max | **46.45** | **4.95** |

Страницы на глубину не реагируют вовсе — постраничная заливка работает. Растёт
не воксельная память, а всё, что заведено на чанк: модель (таблица страниц плюс
две стопки граничных бит — около 8 КБ), меш-задание, инстанс в буфере.

**Спайк 46 мс сидел в куске, который никто не мерил.** В `renderer` между началом
кадра и `buffer_pool_update` вызывался `sync_meshes_` — сбор готовых мешей и
заказ новых, — и он не попадал ни в одну строку отчёта. Теперь это стадия
`mesh_sync`, она же в отладочном окне. На −192 её p50 — 0.036 мс, а max — 3.98.

**Периодическая чистка мешей заменена на непрерывную.** `sweep_orphaned_`
проходила всю таблицу моделей раз в шестьдесят кадров; теперь она идёт срезом
таблицы каждый кадр (курсор по корзинам, не по итератору — вставка между кадрами
может перехешировать таблицу) с потолком в 32 освобождения за кадр. Что это дало
и чего не дало, по трём прогонам `flythrough`:

| | RAM пик | `mesh_sync` max |
|---|---|---|
| чистка раз в 60 кадров | 609 МБ | 3.16 мс |
| чистки нет вовсе | **1 348** | **1.06** |
| срезом каждый кадр | **581** | 3.4–4.0 |

Прогон без чистки — это измерение того, сколько памяти держат осиротевшие меши:
740 МБ за 4000 кадров. Непрерывная чистка забирает их сразу, и пик падает с 609
до 581 МБ.

**А вот спайк она не убрала, и выдавать её за исправление спайка нечестно.**
Ограничение числа освобождений за кадр максимум не сдвинуло: 3.16 → 3.4 → 3.98
при разбросе `max` между прогонами того же порядка. То есть оставшийся выброс —
один кадр из четырёх тысяч — сидит в чём-то другом внутри `sync_meshes_`, и
проверенные догадки (блокирующий деструктор `std::future`, удержание очередного
мьютекса воркером во время мешинга) не подтвердились: очередь построена на
`promise`, а мьютекс отпускается до генерации.

## Поверхность слоями

Поверхность была одной высотой и покраской по глубине: `continent >= 0.7` — всё
камень, `depth == 0` — трава. Теперь земля лежит на камне:

- `stone_height_at` — рельеф камня;
- `soil_depth_at` — толщина почвы: шум, умноженный на крутизну склона и на
  высоту;
- поверхность = камень плюс почва.

Гора получается там, где камень поднялся выше, чем держится почва; правила «если
это гора» в коде больше нет. Крутизна берётся конечной разностью по сетке высот,
которая и так считается: профиль колонки расширен апроном в один воксель, это
+6 % выборок шума вместо ×3.

Ниже поверхности — слои по абсолютной высоте: выветренный камень на четыре
вокселя вглубь, `gray_3` до −32, `gray_2` до −128, `gray_1` до бедрока. Это
заодно ориентир — по цвету стены видно, где ты.

`tests/world/surface.test.cpp` проверяет стопку материалов на выключенных
пещерах: под поверхностью нет дыр, дёрн ровно в один воксель, земли под голым
камнем не бывает, снег только выше снеговой линии, слои породы лежат на своих
отметках. Третий тест поднимает предел крутизны и показывает, что голый камень
наверху — это склон, а не отсутствие почвы в шуме.

## Откуда бралось пять гигабайт

Отчёт печатает теперь и commit charge рядом с working set, и разбивку буферов по
классам размера. Первое же число объяснило жалобу: на глубине 512, сцена
`parked`, **working set 808 МБ при commit 4321 МБ**. Диспетчер задач в колонке
«Память» показывает первое, в «Размер выделенной памяти» — второе.

Виноват один `reserve`. Мешер резервировал под вершины четверть объёма чанка —
65 536 вершин и столько же индексов, 768 КБ, — независимо от того, есть ли в
чанке хоть одна грань. А поскольку векторы **уносятся** из рабочей памяти
воркера в готовый меш (`std::move`), эта ёмкость уезжала с каждым мешем и жила,
пока меш не загрузят на GPU. Медианный чанк даёт около четырёх тысяч вершин,
то есть резерв был завышен раз в шестнадцать.

| `parked`, глубина 512 | резерв 65536 | резерв 4096 |
|---|---|---|
| commit | 4321 МБ | **1126** |
| working set | 808 МБ | **437** |
| мешинг, всего | 6 910 мс | **4 410** |
| мешинг p50 | 280 мкс | **241** |

Мешинг подешевел заодно: 768 КБ свежих страниц на каждое задание — это не только
память, но и время на их первое касание.

**Подсказка по предыдущему чанку измерена и отвергнута.** Логично было бы брать
размер прошлого меша вместо константы, но соседние чанки похожи только по
горизонтали: один поверхностный чанк задирает подсказку, и её наследуют пустые
чанки под ним. Вышло хуже константы по обоим числам — 266 мкс и 1322 МБ против
241 и 1126.

**Связность считалась впустую.** `build_chunk_links` строился на каждом меше,
хотя обход по связности выключен по умолчанию. Теперь это флаг в `mesh_options`,
который рендерер ставит из состояния каллинга. Цена, замеренная отдельным
прогоном: 4 862 → 4 393 мс на всём мешинге, около десятой части.

### Что осталось в памяти и чем это ужимать

На глубине 512, `parked`, после обеих правок: RAM 437 МБ, commit 1126 МБ, VRAM
539 МБ. Разбивка геометрии по классам размера:

```
  total 438 MB of slots, about 215 MB of it geometry
```

То есть **половина видеопамяти под геометрию — это воздух**: меш ложится в слот
со степенью двойки по вершинам и по индексам и занимает его целиком, а классы
растут удвоением ёмкости. Самый крупный класс держит 192 МБ при заполнении 0.55
по вершинам.

Рычаги по убыванию отдачи:

1. **Квад вместо четырёх вершин и шести индексов.** Сейчас 4 × 8 байт вершин
   плюс 6 × 4 байта индексов = 56 байт на квад. Одна запись на квад (позиция,
   размер, нормаль, материал, AO) — 8–12 байт, индексный буфер не нужен вовсе,
   вершинный шейдер разворачивает шесть вершин из `gl_VertexIndex`. Вчетверо-
   впятеро меньше геометрии и столько же полосы на загрузку.
2. **Мельче классы размера** (шаг 1.5 вместо 2) или настоящий субаллокатор.
   Заполнение 0.55–0.88 по замеру, отсюда −20…30 % слотов малой кровью.
3. **Не заводить ничего на сплошной чанк.** На глубине 512 это семь чанков из
   девяти: снимается модель, меш-задание, сущность и инстанс.
4. **Ужать `asset::model`.** Из восьми килобайт на чанк шесть — это
   `neighbor_faces_` и `own_faces_`, двенадцать плоскостей по 512 байт. Они
   нужны только на время мешинга и выводимы из occupancy соседа.

## P11.1: один проход мешера вместо трёх с половиной

Было: `meshing: 12 968 chunks` при `terrain: 3 594 chunks` — каждый чанк мешился
в среднем 3.6 раза. Причина в `world_grid_system::integrate_completed_columns_`:
приходящая колонка отдавала граничный срез уже существующим соседям и ставила
каждому отложенный перемеш. Горизонтальных соседей четыре — отсюда до пяти
проходов по чанку в середине области.

Стало: колонка попадает в **стейджинг** и ждёт, пока сгенерируются все четыре
соседние. Только тогда её чанки получают границы — сразу окончательные — и
кладутся в сетку. Отложенных перемешей больше нет вовсе. Активный набор шире
видимого на одну колонку: кайма существует, чтобы кольцо внутри неё знало свои
границы, и сама не рисуется.

Колонка, ушедшая из зоны отрисовки, но ещё нужная соседям как кайма, не
выгружается, а **разжалуется** обратно в стейджинг: сущности, меши и инстансы
освобождаются, модели остаются. Без этого трейлинг-кольцо выгружалось и
генерировалось заново — на облёте это было 3 139 сгенерированных колонок вместо
1 909.

Сцена `parked`, глубина 512, дальность вида 10:

| | было | стало |
|---|---|---|
| меш-заданий | 12 968 | **3 594** (ровно по чанку) |
| мешинг, всего | 4 410 мс | **936** |
| мешинг p50 | 241 мкс | **118** |
| RAM | 437 МБ | **368** |
| VRAM | 539 МБ | **524** |
| колонок сгенерировано | 441 | 529 (кайма) |
| frame p50 | 0.991 мс | 0.996 |

Облёт: меш-заданий 39 646 → **12 819**, мешинг 14 848 → **3 449 мс**, RAM пик
472 → **381 МБ**, frame p50 1.250 → **1.082**, max 5.944 → **3.796**.

**Вчетверо, а не вдвое — из-за ошибки, которую нашёл тест.** Первая версия
вынимала колонку из стейджинга до обмена границами, и её собственные ещё не
уложенные чанки переставали находиться: вертикальные грани внутри колонки
считали, что над ними воздух. Меш при этом выглядел правильно (снаружи этих
граней не видно), но мешер честно строил маски и выпускал квады внутри сплошного
камня. С правильными границами чанк в толще породы не даёт ни одной грани, и
слой отсекается сразу — отсюда p50 в 118 мкс вместо 241.

Тесты в `tests/world/column_staging.test.cpp`: чанк после укладки больше не
переиздаётся (это и есть «мешится один раз» — мешер ключует меш по
`model_identity`), у уложенного чанка проставлены границы ко всем существующим
соседям (этот и поймал ошибку выше), кайма сгенерирована и не уложена.

## P11.2: чанк в толще породы не заводится вовсе

После P11.1 чанк, замурованный со всех шести сторон, всё равно проходил весь
путь: модель, сущность с тремя компонентами, узел в дереве пространственного
индекса, меш-задание, обход в `buffer_pool_update`. Возвращал он при этом ноль
квадов. На глубине 512 таких **две трети**.

Признак дешёвый и берётся из таблицы страниц, а не из вокселей:
`model::scan_fill` отвечает «воздух / камень / смесь» по 512 записям с выходом на
первых двух различных, а `model::boundaries_are_solid` проверяет, что все шесть
соседних плоскостей известны и заполнены целиком. Воздух не даёт граней никогда;
сплошной камень — только там, где соседа нет или в нём дырка. Ответ окончателен
уже в момент укладки: границы к этому времени проставлены (это и есть P11.1), и
под чанком они не меняются.

Чанк без граней не получает сущности. Воксели остаются на месте — мир по-прежнему
можно копать, физика и `get_voxel` работают через сетку, а не через сущности, —
и первый же `world_grid::set_voxel` заводит сущность через `ensure_entity`.

Сцена `parked`, глубина 512, дальность вида 10. Обе колонки одним билдом, разница
только во флаге:

| | все сущности | P11.2 |
|---|---|---|
| чанков в сетке | 3 594 | 3 594 |
| из них с сущностью | 3 594 | **1 187** |
| квадов | 3 889 468 | **3 889 468** |
| мешинг, всего | 1 010 мс | **832** |
| мешинг p50 | 127 мкс | 608 |
| RAM | 366 МБ | **239** |
| commit | 1 085 МБ | **886** |
| VRAM | 524 МБ | 524 |
| слотов в буферах | 424 МБ | 424 |

**Квады совпали до единицы** — это и есть проверка, что ничего не потерялось:
геометрия та же, платим за неё втрое меньшим числом сущностей.

Мешинг упал только на 18 %, а не втрое: отсечённые чанки были самыми дешёвыми.
После P11.1 замурованный чанк выходил из мешера примерно за 43 мкс — построить
occupancy и убедиться, что маски пустые. Медиана выросла со 127 до 608 мкс именно
поэтому: в выборке остались одни настоящие чанки. Настоящая цена этих двух с
половиной тысяч чанков была не в мешере, а в памяти: **RAM −35 %**.

Облёт: меш-заданий 12 819 → **3 025**, мешинг 3 449 → **1 717 мс**, RAM пик
381 → **243 МБ**, frame p50 1.082 → **1.023**, max 5.774 и 2.218 в двух прогонах
(разброс тот же одиночный выброс, что и раньше, — 3.796 из P11.1 лежит между
ними).

**Одно место пришлось чинить отдельно.** Обход связности (`P5.1`) читает links по
сущности чанка, и «сущности нет» там означало «ничего не известно», то есть
«открыто настежь» — взгляд пошёл бы сквозь коренную породу. Теперь
`combined_buffer_pool` спрашивает `chunk::is_solid()` раньше таблицы и отдаёт
запечатанную ячейку. Ответ тот же, что давал бы мешер (`build_chunk_links` на
сплошном чанке не находит ни одного кармана), только без мешера. На облёте с
`--chunk-cull`: 639 из 1 197 чанков видимы, 46.6 % скрыто.

**Чего это стоило.** Сплошные чанки ушли из пространственного индекса, поэтому
луч камеры от третьего лица через них проходит насквозь. Достать до этого можно,
только стоя вплотную к плоскости раздела между пещерой и монолитом: стена, в
которую упирается луч, почти всегда принадлежит смешанному чанку и в индексе
осталась. Столкновения игрока это не трогает — они идут через `world_grid`
напрямую.

Тесты: `tests/world/model_fill.test.cpp` — таблица страниц отвечает про воздух,
камень и смесь, шесть сплошных соседей закрывают чанк, дырка в плоскости соседа
его открывает, а воздух на воксель глубже — нет. В
`tests/world/column_staging.test.cpp` добавлены два: у каждого чанка без сущности
либо весь объём пуст, либо все шесть швов сплошные (проверено по вокселям
соседа, а не по кэшированной плоскости), и воксели такого чанка на месте. Дно
теста пришлось опустить до −192: нижний чанк мира открыт снизу в пустоту и
рисуется, так что колонке из трёх чанков нечего было хоронить.

`try_place_camera` брала высоту поверхности ровно в точке (0, 0) и добавляла три

## P11.7: граничные плоскости не живут в модели

Из восьми килобайт на чанк шесть были двумя массивами по шесть плоскостей 64×64:
`own_faces_` (что этот чанк показывает соседям) и `neighbor_faces_` (что соседи
показывают ему). Оба нужны на отрезке от укладки до готового меша, а лежали
столько, сколько жив чанк.

`own_faces_` не стало вовсе. Вместо предвычисленного массива —
`model::extract_face`, который собирает плоскость прямо из таблицы страниц:
однородная страница даёт восемь строк по восемь бит без единого обращения к
вокселю, разреженная резолвится один раз на страницу, а не на воксель. Число
построений плоскостей то же самое (шесть на чанк), просто теперь они строятся в
момент, когда нужны, а не заранее.

`neighbor_faces_` переехали за `unique_ptr` (`model_boundary`) и освобождаются,
как только последний читатель закончил: мешер отпускает их в
`mesh_pool::process_completed`, а чанк, который P11.2 решил не заводить,
отпускает сразу — таких две трети, и без этого семь мегабайт остались бы висеть.

Сцена `parked`, глубина 512, дальность 10:

| | P11.2 | P11.7 |
|---|---|---|
| RAM | 240 МБ | **212** |
| commit | 988 МБ | **949** |
| генерация колонки p50 | 2 304 мкс | **1 427** |
| генерация, всего | 1 365 мс | **845** |
| мешинг, всего | 637 мс | 621 |
| квадов | 3 889 468 | **3 889 468** |
| VRAM | 524 МБ | 524 |
| frame p50 | 0.989 мс | 0.980 |

Облёт: RAM пик 243 → **214 МБ**, квадов те же 9 925 585.

Генерация подешевела на 38 %, потому что из воркера ушёл проход
`compute_own_boundaries` — шесть плоскостей по 4 096 вызовов `is_empty` на чанк.

**За что заплатили.** Сборка плоскостей переехала с воркера генератора (их
четыре, и они вне кадра) на главный поток, в укладку колонки:
`grid_boundary_from` p95 0.016 → 0.075 мс, p99 → 0.102. Это одна колонка на кадр,
54 шва. Цену снижали дважды и оба раза мерили:

- признак «сплошной / воздух / смесь» кешируется в модели и греется на воркере
  генератора, пока страницы горячие; сплошному соседу плоскость не разбирают, а
  заполняют. Сначала то же самое сделали **без** кеша — 0.096 → 0.116 мс, то есть
  ничего: платим не за биты, а за две холодные килобайты таблицы страниц соседа.
  С кешем 0.086;
- разреженная страница в `extract_face` резолвится один раз, а не на каждый из
  64 вокселей: 0.086 → 0.069.

Остаток — обращения к холодным таблицам страниц смешанных соседей, и убрать его
можно только одним способом: отдавать мешеру сами модели соседей и строить
плоскости на его потоке. Это трогает путь заказа меша в рендерере и оставлено
на потом.

**Разрушаемость от этого не пострадала — наоборот.** Плоскость это кеш над
вокселями соседа, а воксели никуда не делись. Хранить копию, снятую в момент
укладки, для правки как раз бесполезно: изменился-то сосед, и копия стала
неверной. Поэтому `world_grid::set_voxel` теперь пересобирает плоскости заново:
себе все шесть, и соседу через тот шов, на котором стоял воксель, — после чего
обе модели идут на перемеш. Тест «digging a seam tells both sides» выкапывает
воксель на шве между двумя замурованными чанками и проверяет, что оба вернулись
в сцену, а сосед видит в своей плоскости дырку ровно на месте выкопанного вокселя
и камень рядом с ней.

Чанк помнит, о каких соседях ему рассказали при укладке (`known_neighbors`) —
плоскостей уже нет, а факт нужен: на нём держится проверка P11.1 о том, что
уложенный чанк знает всё своё окружение.

## P11.3: квад вместо четырёх вершин и шести индексов

Квад стоил 4 × 8 байт вершин плюс 6 × 4 байта индексов — 56 байт на прямоугольник,
и вся эта арифметика лежала в видеопамяти. Теперь одна запись на квад: два
`uint32` с двумя углами коробки по семь бит на компоненту, направлением грани,
палитрой и масками AO. **Восемь байт вместо пятидесяти шести.**

Разворачивает квад в четыре вершины вершинный шейдер: он читает запись из
storage-буфера по `gl_VertexIndex / 4`, берёт угол по `gl_VertexIndex % 4` и
выбирает компоненты из `min` или `max` по той же таблице `face_verts`, которую
раньше запекал мешер. Индексный буфер остался, но он **один на весь движок**: его
содержимое — повторяющийся узор `0,1,2,2,3,0`, а на нужные квады его сдвигает
`vertexOffset` команды отрисовки. Полтора мегабайта вместо 24 байт на квад.

Сцена `parked`, глубина 512, дальность 10:

| | P11.7 | P11.3 |
|---|---|---|
| байт на квад | 56 | **8** |
| VRAM | 524 МБ | **169** |
| слотов в буферах | 424 МБ | **71** |
| из них геометрии | 214 МБ | **30** |
| commit | 943 МБ | **402** |
| gpu_world_pass p50 | 0.674 мс | **0.624** |
| gpu_frame p50 | 0.813 | **0.697** |
| frame p50 | 0.995 | **0.923** |
| мешинг, всего | 693 мс | **567** |
| квадов | 3 889 468 | **3 889 468** |

Облёт: VRAM 526 → **169 МБ**, мешинг 1 580 → **1 391 мс**, frame p50 1.078 →
**1.026**, квадов те же 9 925 585.

**Сначала было без индексов вовсе.** Шесть вершин на квад из `gl_VertexIndex`,
`VkDrawIndirectCommand`, никакого индексного буфера — и **gpu_world_pass 0.674 →
0.931, плюс 38 %**. Причина простая: шесть вершинных вызовов на квад вместо
четырёх, и повторного использования вершин между двумя треугольниками нет. Общий
индексный буфер возвращает четыре вызова и кэш после трансформации, а памяти
стоит полтора мегабайта на весь пул. После него мировой проход стал **быстрее**
исходного: данных на вершину меньше, а индексы у всех одни и те же и всегда
горячие.

**Две ошибки по дороге, обе стоили по прогону.**

Первая: узор индексов я сначала лил через кольцо стейджинга кадра. У
`staging_buffer::stage` проверка границ — это `assert`, то есть в Release её нет:
мегабайт индексов ушёл мимо окна кадра и лёг поверх данных соседнего кадра.
Испорченные команды отрисовки дали **мировой проход в 35 мс**. Узор пишется в
свой host-visible буфер и копируется устройством, минуя кольцо.

Вторая: буфер-источник копии я заменял на месте. Копия к этому моменту только
записана в список, а за один кадр появляется несколько классов размера — второй
вызов убивал буфер под неотправленной копией. `ErrorDeviceLost` на первом же
кадре облёта; нашла это валидация (`VUID-vkCmdCopyBuffer-srcBuffer-parameter`),
запущенная через `VK_LOADER_LAYERS_ENABLE`, потому что слои включаются только в
Debug. Старый источник теперь уходит в очередь удаления.

Заодно включена фича `drawIndirectFirstInstance`. Команды отрисовки всегда
писали в `firstInstance` индекс инстанса — это то, чем кормится пер-инстансный
вершинный атрибут, — а фича не запрашивалась ни разу.

**Чем это проверено.** Число квадов совпадает до единицы в обеих сценах, оба
дифф-теста мешера (жадный против повоксельного) зелёные, дайджесты пересняты —
геометрия та же, изменилась только упаковка. Валидация на облёте молчит.
Картинку глазами я не проверял: тесты покрывают содержимое мешей, а не то, что
шейдер из них рисует.

## P11.9: грани, смотрящие от камеры, не доходят до вершинного шейдера

Мешер выпускает квады строго по направлениям — `for (face_direction = 0..5)`, —
то есть меш это шесть подряд идущих диапазонов. Достаточно запомнить шесть длин
(`mesh::face_counts`), и вместо одной команды отрисовки на чанк писать шесть, по
одной на направление. Дальше compute-шейдер отсечения пропускает те, что
смотрят от камеры: грани осевые, поэтому целое направление отброшено, когда
камера по эту сторону всей коробки чанка (`eye.x <= bmin.x` для +X и так далее).
Камера внутри коробки — обе стороны оси остаются.

Сколько это вообще может дать, померено на настоящем ландшафте с проставленными
границами (128 чанков, 40 с геометрией — те же 31 %, что в бою):

| грань | доля квадов |
|---|---|
| +Y | 34.9 % |
| −Y | 4.2 % |
| +X / −X | 13.6 / 16.3 |
| +Z / −Z | 17.7 / 13.3 |

Сверху вниз отваливается **33.8 %**, снизу вверх — 64.5 %.

Сцена `parked`, глубина 512, дальность 10:

| | P11.3 | P11.9 |
|---|---|---|
| gpu_world_pass | 0.624 мс | **0.488** |
| gpu_world_geometry | 0.608 | **0.473** |
| gpu_frame | 0.697 | **0.638** |
| frame p50 | 0.923 | **0.778** |
| gpu_compute_cull | 0.14 | 0.15 |

Облёт: frame p50 1.026 → **0.883**, gpu_world_pass p50 0.451 → **0.371**.

Проход подешевел на 22 % при 34 % убранных квадов — остальное не масштабируется
с их числом. Отсечение стало чуть дороже: команд оно теперь выпускает до трёх на
чанк вместо одной, это около сотой миллисекунды против 0.136 сэкономленных.

Данных это не стоило ничего: шесть `uint32` на меш, которые всё равно считались
при мешинге. Растеризатор эти грани выбрасывал и раньше — но уже после
вершинного шейдера.

**Теневые каскады не тронуты.** Там сторона определяется светом, а не камерой, и
невидимый камере чанк всё равно отбрасывает тень; проверка стоит только на
проходе 0. `gpu_shadow_pass` на этих сценах и так 0.000–0.149 мс, так что повода
рисковать нет. Обход связности (`--chunk-cull`) складывается с этим без
изменений: те же 639 из 1197 видимых, 46.6 % скрыто.

## P11.4: страница на пробег вместо `get_voxel` на грань — не работает

Битовый путь мешера брал `mdl.get_voxel(mx, my, mz).id` на каждую видимую
ячейку. Идея пункта: вдоль строки слоя двигается ровно одна модельная ось,
значит страница меняется раз в восемь ячеек, и её можно разрешить один раз на
пробег, а для однородной страницы не трогать воксели вовсе.

Сделано и откачено. Замер на 72 чанках настоящего ландшафта с проставленными
границами, однопоточно, пять раундов в прогоне:

| | медиана прогона |
|---|---|
| `get_voxel` на ячейку | 15.63 / 15.60 / 15.46 мс |
| страница на пробег | 15.66 / 15.53 / 15.61 |

Разброс внутри прогона 0.1 мс, между прогонами 0.2. **Разницы нет.**

Предпосылка пункта оказалась неверной. `model::get_voxel` объявлен в интерфейсе
модуля и разворачивается инлайном; таблица страниц чанка это два килобайта, она
не покидает L1, и поиск в ней — пара сдвигов и загрузка. Курсор добавляет три
деления, три сравнения и хранимое состояние, то есть ровно ту же работу, что
экономит.

Отдельно стоит сказать про методику: первый прогон базовой версии дал 16.43 мс и
выглядел как честное −6 % в пользу курсора. Повторы той же сборки дали 15.14 и
15.16. То есть один прогон здесь не значит ничего, а вывод из пары «до/после»
без повторов был бы противоположным правильному.

Следствие: цена ячейки лежит не в поиске страницы, а в AO и в записи маски.
P11.5 (`build_occupancy` для однородного чанка) опирается на ту же предпосылку и
скорее всего тоже ничего не даст.

## P11.10: набивка слотов, и барьер, который нашёлся по дороге

После P11.3 в буферах лежало 71 МБ слотов ради 30 МБ геометрии. Разбивка по
классам показала, что 41 МБ потерь делятся почти пополам и лечатся разным:

| источник | сколько | видно по |
|---|---|---|
| незанятые слоты | ~26 МБ | класс 8192: 271 слот из 512 |
| набивка внутри слота | ~13 МБ | класс 16384: load 0.57 |

Три правки, каждая померена отдельно:

1. **Ёмкость растёт в полтора раза, а не вдвое.** Буфер стоит там, где его
   оставил последний рост, поэтому при удвоении пустует от нуля до половины —
   на главном классе намерено 47 %. **71 → 59 МБ.**
2. **Классы размера тоже в полтора раза.** Меш держит весь свой класс, сколько
   бы ни занимал; при удвоении в среднем четверть слота пустая, на классе с
   самыми большими чанками — 43 %. Степени двойки здесь ничем не обязаны:
   геометрия это storage-буфер, читаемый по индексу, а не вершинная привязка.
   **59 → 43 МБ**, load по классам с 0.57–0.84 до 0.75–0.89.
3. **Начальная ёмкость по байтовому бюджету, а не 32 слота.** Фиксированное
   число слотов заставляло крупные классы держать мегабайты ради горстки мешей —
   класс 18698 держал 4.6 МБ ради пяти. **43 → 39 МБ.**

Сцена `parked`, глубина 512, дальность 10:

| | P11.9 | P11.10 |
|---|---|---|
| слотов в буферах | 71 МБ | **39** |
| из них геометрии | 30 МБ | 30 |
| доля занятого | 0.42 | **0.77** |
| VRAM | 169 МБ | **140** |
| commit | 400 МБ | **352** |
| gpu_compute_cull | 0.149 мс | **0.022** |
| gpu_frame | 0.638 | **0.510** |
| frame p50 | 0.778 | **0.641** |
| gpu_world_pass | 0.488 | 0.487 |

Облёт: frame p50 0.883 → **0.740**, VRAM 169 → **150 МБ**. Слотов там 49 МБ, а не
39: стриминг оставляет больше свободных слотов, и между классами они не
переезжают.

**Барьер.** Мелкие классы подняли число буферов с девяти до пятнадцати, и
`gpu_compute_cull` подскочил с 0.149 до 0.243 мс — вся выгода P11.9 по кадру
съедена. Причина оказалась не в отсечении, а в том, что `cull_pipeline::dispatch`
вызывался на каждый буфер и каждый раз ставил `pipelineBarrier` между обнулением
счётчиков и compute. Барьер — это остановка конвейера, и пятнадцать барьеров
подряд просто сериализовали проход. Теперь обнуление всех счётчиков идёт одним
блоком, барьер один на всех, дальше пятнадцать диспатчей подряд: **0.243 →
0.022 мс**. Это не возврат к прежнему, а в семь раз дешевле, чем было при девяти
буферах — стоял он там всё это время.

## Окклюзия по HZB: собрана, не заработала, откачена

Сделана целиком и снята: пирамида глубины (`depth_pyramid`, шейдер редукции
`hzb_reduce.comp`), проброс в `cull.comp` и тест AABB против неё на проходе
камеры. В дереве этого больше нет — база вернулась к своим числам ровно
(gpu_world_pass 0.488, gpu_frame 0.510, VRAM 141 МБ), 176/176 зелёные.

**Что успело подтвердиться.**

- Механика отсечения работает: с `occluded()`, принудительно возвращающим
  `true`, мировой проход падает 0.490 → **0.217 мс**. То есть команды на проходе
  0 действительно перестают выпускаться, и выигрыш есть куда получать.
- Пирамида дешёвая: **0.028 мс** на кадр за одиннадцать уровней 640×360 →
  1×1, включая барьеры между уровнями.
- Глубина пригодна: без MSAA, D32, reversed-Z, одна картинка на все кадры.
  Понадобились только `eSampled` в usage и `storeOp = eStore`.

**Ошибка, которая стоила дороже всего.** В `cull_frustum_ubo` добавилась
`mat4 prev_view_proj`, и с ней **весь блок поехал**: шейдер читал `pass_count`
мусором, писал команды за пределы своего буфера, мировой проход подскакивал до
**34 мс** даже при полностью отключённом тесте. Смещения, посчитанные по
std140, совпадали с C++ до байта (592 в обоих), и всё равно совпадения не было.
Замена `mat4` на `vec4 prev_view_proj[4]` с тем же содержимым вылечила всё
мгновенно. Матрица в uniform-блоке — единственный член, о раскладке которого
хост и шейдер здесь расходятся; больше в этих блоках их быть не должно.

**На чём остановилось.** Пирамида пишется, но `cull.comp` её не видит: если
редукция кладёт в каждый тексель константу `1.0`, тест `farthest > 0.0` не
отсекает ничего, то есть чтение возвращает нули. Значит расходятся стороны
записи и чтения одного и того же изображения — разные views одного `VkImage`,
`level_views_[i]` на запись и `chain_view_` на чтение. Дальше это диагностируется
кадровым отладчиком за пять минут и гаданием по шейдеру — за часы, поэтому
работа снята, а не оставлена наполовину: тест, отсекающий весь мир, хуже, чем
его отсутствие.

**Чего ждать от неё, когда вернёмся.** На этих двух сценах — немного. Обе
смотрят с высоты, а бокс чанка это 512 единиц мира: чтобы спрятать такой
целиком, нужен очень большой заслон. Обход связности прятал 46.6 % не потому,
что он умнее, а потому что работал по карманам в 32 вокселя. Значит смысл
появляется вместе с кластерами — диапазонами по несколько десятков квадов со
своим AABB, — и вот на них окклюзия и должна окупаться.

## P11.8: колонка сверху вниз

`gen_column` хранит чанки в `std::map` с `std::greater`, то есть каждый обход
колонки — генерация, обмен границами, укладка — идёт от неба вниз. Раньше это
был `unordered_map`, и порядок был произвольным.

Кадр, мешинг и генерация не изменились, как и ожидалось: работы столько же.
Смысл в другом — из девяти чанков колонки виден обычно один, поверхностный, и
теперь он мешится первым. Небесный свет пойдёт тем же путём, а карта высот
(`column_profile::surface`) для него уже есть. Настоящая проверка будет, когда
появится свет.

## Пещеры на шуме: поля-кластеры

Третья форма пещер, и первая на шуме, которая устояла. Устройство: **поле** —
трёхмерный шум низкой частоты, приплюснутый по Y, — говорит, где порода вообще
полая; между полями камень сплошной. Внутри поля работают два слагаемых одного
значения: **каверны** (`|шум| < ширина`, шум сжат по Y, так что зал шире, чем
выше) и **ходы** (два независимых поля, оба около нуля — их общий ноль это кривая,
а кривая и есть тоннель; одно поле дало бы простыню). **Этажи** — полоса, которая
расширяет каверны на фиксированных высотах, так что поле читается уровнями.

Значение считается на сетке через 4 вокселя и читается трилинейной
интерполяцией: по вокселю это четыре трёхмерных выборки на каждый воксель мира,
по сетке — одна на шестьдесят четыре. Ячейка, у которой все восемь углов в
породе, пропускается целиком.

Замер на четырёх участках карты 5×5 колонок:

| участок | воздух | проходимо | просторно | систем | крупнейшая | с неба | граней/квокс |
|---|---|---|---|---|---|---|---|
| 0,0 | 1.46 % | 0.43 | 0.14 | 864 | 0.45 | 0.05 | 11.4 |
| 16,8 | 1.27 | 0.42 | 0.15 | 797 | 0.35 | 0.32 | 10.3 |
| 40,24 | 1.67 | 0.45 | 0.17 | 891 | 0.19 | 0.29 | 12.4 |
| 64,64 | 1.43 | 0.44 | 0.15 | 672 | 0.20 | 0.54 | 11.0 |

Против систем-камер: воздуха вчетверо больше (было 0.2–0.55 %), проходимость
такая же (0.41–0.58), просторность ниже (было 0.13–0.28), крупнейшая система
держит пятую-половину — то есть кластеры сохранились, единого подземелья не
возникло. Пещеры теперь стоят на всей глубине, а не свисают с поверхности.

**Три вещи пришлось найти замером, а не рассуждением.**

Пороги шума взяты с потолка не работают: первая настройка дала 9.5 % воздуха и
один связный подземный мир на весь участок, вторая — 0.3 % и одни щели
(проходимость 0.09). Форма правильная где-то посередине, и найти её можно только
по таблице.

Поле сначала было двумерным — колонка либо с пещерами на всю глубину, либо без.
Это дало **3 113 нарисованных чанков из 3 594** (против 1 187) и генерацию
**43 мс на колонку**. Трёхмерное поле и пропуск сплошных ячеек вернули то и
другое.

Входы не получаются как поблажка существующему полю. Две попытки подряд —
«не штрафовать крышу в пятнах» и «поднимать значение в пятнах» — оставляли по
два участка карты из четырёх с крупной системой и без единого выхода наружу.
Работает только вход как **самостоятельное поле**: пятно проницаемой крыши несёт
собственное поле на 110 вокселей вниз, то есть шахту, и она либо находит блоб,
либо остаётся воронкой. Плюс само поле смещено вверх у поверхности — карст и в
природе гуще там.

**Цена.** Сцена `parked`, глубина 512, дальность 10:

| | камеры | шум |
|---|---|---|
| frame p50 | 0.685 мс | **1.683** |
| gpu_world_pass | 0.493 | **1.118** |
| нарисованных чанков | 1 187 | **2 669** |
| квадов | 3.9 М | **9.2 М** |
| VRAM | 141 МБ | **220** |
| RAM | 212 МБ | **278** |
| генерация колонки p50 | 1 377 мкс | **3 834** |
| до готовности | 452 кадра | 707 |

Облёт: frame p50 0.740 → **1.762**, VRAM 150 → **229 МБ**.

Фаза 11 разгоняла кадр с 0.99 до 0.685 мс; пещеры забрали этот запас и ещё
столько же. Это сознательный размен: мир с пещерами на всю глубину дороже мира,
у которого две трети чанков — сплошной камень.

**И одно, что размена не стоит.** Камера вплотную к изрытой породе рисует
**60–130 мс на кадр**. Нашлось это дважды: облёт летел на фиксированной высоте и
входил внутрь холмов (100 мс), а `parked` при более частых входах оказался над
раскрытой воронкой (67 мс). Геометрия сцены при этом та же — меняется только то,
сколько её попадает в кадр вблизи и с каким перекрытием. Ни настройкой пещер, ни
форматом квада это не лечится: нужна окклюзия. До неё сцена облёта поднята на
400 единиц над землёй, чтобы мерить стриминг, а не стену пещеры перед носом; из-за
этого её числа не сравнимы с прежними.

Порог входов пришлось поставить в 0.21: на 0.17 участок 0,0 получает выход, но
`parked` встаёт над ним и кадр уходит в 100 мс. Это тот же вывод с другой
стороны.

## Сцены `spin` и `advance`, и просадки, которые они нашли

Две сцены к обязательному прогону. `parked` и `flythrough` обе смотрят с высоты и
обе ведут камеру плавно, поэтому целый класс просадок в них не попадал.

- **`spin`** — камера стоит на месте и поворачивается по горизонту. Ничего не
  стримится и ничего не движется, так что всё, что здесь стоит времени, это цена
  посмотреть в другую сторону.
- **`advance`** — камера идёт по прямой всё время прогона, 13 единиц за кадр, то
  есть входит в новую колонку каждые сорок кадров. Облёт ходит по кругу и
  возвращается по своим следам; эта — никогда.

**Что нашлось.** На `spin` перерисовка теневых каскадов: `cascades drawn` p50 = 0,
но p99 = **4**, и `gpu_shadow_pass` с 0.000 уходил в 1.39 мс. Каскад привязан к
центру среза фрустума, а центр сидит далеко по оси взгляда — поворот на месте
гоняет его по широкой окружности, и все четыре каскада вылетают за свой padding
одновременно.

**Первая правка: каскад привязан к позиции камеры, а не к середине среза.** Тогда
поворот не меняет ничего — устаревает только от ходьбы. Шар должен доставать до
дальних углов среза, а не только до своих, то есть примерно в 1.6 раза больше
радиусом: это разрешение, заплаченное за кадр без рывка. Те же 1.6 стоило бы
просто расширить padding, но это сделало бы перерисовки реже, а не убрало.

**Вторая правка: потолок перерисовок за кадр распространён на принудительные.**
Бюджет `max_cascade_updates_per_frame_` был, но каскад, вышедший из покрытия,
проходил мимо него. При ходьбе вперёд все четыре выходят в пределах нескольких
кадров друг от друга и рисовались разом. Теперь «вышел из покрытия» — это высший
приоритет, а не безусловность; каскад, подождавший кадр, устарел на дальнем краю
своего среза, а всплеск виден каждый раз.

`spin`, 2000 кадров:

| | было | центр на камере | + потолок |
|---|---|---|---|
| frame p50 | 1.291 мс | 1.222 | **1.185** |
| p95 | 2.270 | 2.017 | **1.958** |
| p99 | 2.880 | 2.411 | **2.381** |
| **max** | **5.063** | 5.405 | **2.908** |
| cascades drawn p99 | 4 | 0 | 0 |
| gpu_shadow_pass p99 | 1.387 | 0.000 | 0.000 |

`advance` (появилась после первой правки, поэтому в таблице только вторая):

| | до потолка | после |
|---|---|---|
| frame p95 | 3.357 мс | **2.912** |
| p99 | 3.843 | **3.232** |
| **max** | **8.848** | **5.748** |
| cascades drawn p95 | 4 | **2** |
| gpu_shadow_pass p95 | 1.619 | **0.973** |

`parked` и облёт не пострадали: 1.585 и 1.710 p50, каскадов на парковке ноль.

**Что осталось.** На `spin` кадр всё ещё ходит от 1.19 до 1.94: это сам мировой
проход, 0.78 в одну сторону и 1.94 в другую. Не рывок, а разная нагрузка — в
какую-то сторону в кадре просто больше пещер. Лечится это окклюзией, не тенями.

Разрешение теней я глазами не проверял: шар каскада стал в 1.6 раза шире, значит
тень грубее, и насколько это заметно — вопрос к картинке, а не к числам.

## Смена дня и ночи в `test_world_grid`

Солнце едет по дуге, свет и небо идут за ним: полдень белый, у горизонта тёплый,
ночью тусклый синий. Ambient в шейдере берётся из цвета и яркости направленного
света, так что ночь темнеет целиком, а не только тени. `N` останавливает солнце,
`[` и `]` двигают его, в панели есть ползунок времени и длина суток.

Заведено, чтобы посмотреть на тени: каскад после правки на `spin` стал в 1.6 раза
шире, и насколько это заметно, числа не скажут.

**В bench-сценах цикл выключен.** Повернувшееся солнце сбрасывает все каскады, и
замер начал бы мерить солнце, а не то, что проверяют. Проверено прогоном с
временно снятым запретом на `spin`:

| | солнце стоит | солнце едет |
|---|---|---|
| frame p50 | 1.185 мс | **2.263** |
| gpu_shadow_pass p50 | 0.000 | **1.131** |
| cascades drawn p50 | 0 | 2 |

То есть подвижное солнце удваивает кадр: теневой проход перестаёт отдыхать
вообще. Это свойство цикла, а не дефект — при сутках в две минуты солнце уходит
за порог обновления каждый кадр. Если день-ночь однажды понадобится в продукте,
это отдельная статья расходов, и потолок в два каскада за кадр — то, что
удерживает её от учетверения.

## Сцена `crowd`

`--bench=crowd --bench-crowd=N` — N тел с физикой (`rigid_body` +
`box_collider`), у каждого четыре анимированные части в иерархии, то есть 5N
сущностей. Клип строится в коде, ассеты не нужны. Камера неподвижна и смотрит
на толпу.

Тела падают с небольшой высоты и получают 400 кадров на приземление, прежде чем
начнётся замер: сцена, где часть тел ещё в полёте, даёт разную работу в каждом
прогоне. Попытка ставить их сразу на землю оказалась хуже — на неровном рельефе
тела частично утапливаются, и выталкивание стоит дороже падения.

| N тел | сущностей | `world_update` p50 | разброс по 3 прогонам |
|---|---|---|---|
| 10 | 50 | **0.043 мс** | 2 % |
| 50 | 250 | **0.327** | 6 % |
| 200 | 1000 | **1.973** | 9 % |

Рост сверхлинейный: впятеро больше тел — вдесятеро больше времени. При 200 телах
кадр становится **CPU-bound** (2.27 мс против 0.77 мс GPU) — первая сцена в
проекте, где это так. Целевая по PRD «деревня + 10 NPC» укладывается в 0.043 мс,
запас велик.

### P1.7 и P1.8 на этой сцене

`world_update` p50 при N = 200, медиана трёх прогонов:

| | без правки | с правкой | |
|---|---|---|---|
| P1.7, кэш чанка в физике | 2.250 | **1.973** | −12 % |
| P1.8, ключ сортировки | 2.173 | ~1.97 | в пределах шума |

P1.7 подтверждается: направление устойчиво, хотя 12 % при разбросе сцены в 9 % —
на границе. P1.8 на этой сцене не различим: иерархия глубиной один уровень, и
пересчёт глубины в компараторе просто не успевает стать заметным. Правка
остаётся как снятие работы, растущей с глубиной иерархии, но здесь она не
доказана.

### Прежняя формулировка (до появления сцены)

Кэш чанка в `resolve_box_voxel` и сортировки по предвычисленному ключу
(`transform_system`, `combined_buffer_pool`) на этих сценах не проявляются:
физических тел в `test_world_grid` нет вовсе, а `world_update` держится на
0.004 мс. Обе правки убирают работу, растущую с числом сущностей, и их цена

## Что эти числа означают

**Облёт быстрее парковки.** Это не аномалия: припаркованная точка смотрит вдоль
земли и держит в кадре больше плотной геометрии, чем вид с радиуса 1500.
Сравнивать между собой два режима бессмысленно — сравнивают одинаковый режим до
и после правки.

**`begin_frame` — не работа, а ожидание.** 1,56–1,80 мс из ~1,8–2,0 мс кадра
уходят в `waitForFences` (`renderer.cpp:119-122`): CPU ждёт GPU. Собственная
CPU-сторона кадра — порядка 0,25 мс. Отсюда практическое следствие: правки,
экономящие CPU, на этой сцене не видны вообще, а видны те, что разгружают GPU
или убирают синхронные простои.

**`buffer_pool_update` — цена расширения буферов.** В `parked` она равна нулю в
пределах разрешения, в `flythrough` даёт p99 = 0.132 мс и max = 0.506 мс: это
расширение и перенос старого содержимого. Синхронного дренажа очереди там
больше нет — разбор выше.

# M1 — отчёт: `vw.core`

**Дата:** 2026-08-04 · **Ветка:** `modules-migration` · **Статус:** приёмка пройдена

Первая боевая библиотека-модуль. Матрица {MSVC, Clang} × {Debug, Release}
зелёная, во всех четырёх конфигурациях **130/130** тестов.

## Состав модуля

| Партиция | Содержимое |
|---|---|
| `:types` | `uint8..uint64`, `int8..int64`, `float32`, `float64` |
| `:timing` | `measure_ms` |
| `:log` | уровни, `set_level`/`get_level`, `add_file_sink`, `write` |
| `:vector` | `vec2`, `vec3`, `vec4`, `quat`, специализации `std::hash` |
| `:matrix` | `mat4` |
| `:color` | `color`, палитры `colors::` |
| `:math` | `vw::math`, `transform` |
| `:blocks` | `block_id`, `block_type`, `blocks::`, `block_registry`, `voxel` |

В `engine/include/vw/core/` не осталось ни одного `.inl.h` — только шимы и
`tuple_utils.h`, который принадлежит ECS и умрёт в M2 вместе с кортежем
компонентов.

## Ключевая находка: правило порядка включений

Первая попытка переходного режима провалилась: TU потребителей падали лавиной
переопределений в `<memory>`, `<iterator>`, `<array>`, а `std::format_string`
переставал быть вычислимым в constant expression (C7595).

Причина не в «тяжёлых заголовках», как казалось сначала, а в порядке. **MSVC
сливает объявления из global module fragment модуля с текстовыми включениями
потребителя только если текстовое включение идёт раньше импорта.** Подсказку дал
сам код: `logger.h` включал `<format>` до `import` и работал, а шимы векторов не
включали ничего и ломались.

Отсюда `vw/core/detail/module_prelude.h` — он воспроизводит include-набор
модуля, и каждый шим подключает его перед импортом. После этого через границу
проходит что угодно, включая специализации `std::hash`, экспортированные из
модуля. Прелюдия — временная конструкция, она исчезает в M6 вместе со всем
деревом `engine/include/`.

## Уточнение решения D1

`import std` в модульных юнитах откладывается до M6. Пока потребители включают
стандартные заголовки текстуально, импорт модуля `std` в тот же TU обречён: это
не вопрос порядка, а два независимых набора объявлений одних и тех же сущностей.
Модульные юниты берут стандартную библиотеку через global module fragment.

Побочное следствие: слой форматирования логгера остался заголовком
(`vw/log/logger.h`). Шаблоны с `std::format_string` через границу модуля не
переживают `consteval`-проверку формата. В модуле живёт сток — уровни, синки,
`write`.

## Выпил spdlog (D7)

Собственный логгер: шесть уровней по два перегруза (с категорией и без),
консольный синк с цветом через ANSI (на Windows включается virtual terminal),
файловый синк, формат `[YYYY-MM-DD HH:MM:SS.mmm] [level] [category] message` —
тот же, что давал spdlog. Покрыт тремя тестами: файловый синк, рантайм-фильтр
уровня, точность метки времени.

Логгер синхронный, а не асинхронный, как в эскизе плана. Из 73 вызовов 25 сидят
в потенциально пер-кадровом коде, и им нужна не фоновая очередь, а compile-time
отсечение через `VW_LOG_MIN_LEVEL` в `vw/config.h` — тогда в релизе они
исчезают целиком и писать становится нечего. Фоновый поток стоил бы возни с
порядком разрушения статиков ради трафика, которого не будет. По умолчанию
отсечение выключено, поведение совпадает с прежним.

## Что вскрылось попутно

Выпил spdlog разблокировал Clang: её экспортированный конфиг навязывал
`/Zc:__cplusplus` **всем** потребителям, а `clang++` такого флага не знает.
До этого Clang-ветка на реальном проекте не собиралась ни разу — спайк M0 её не
ловил, потому что не зависел от spdlog.

Следом Clang нашёл три ошибки, которые MSVC годами прощал:

1. `<Psapi.h>` включался раньше `<Windows.h>` в `engine.inl.h`; работало только
   потому, что spdlog подтягивал `windows.h` выше по TU.
2. `params p = {}` в объявлении конструктора `perlin_terrain_generator` —
   умолчание по значению вложенного класса нельзя вычислить внутри определения
   объемлющего.
3. Форвард-декларация `vw::transform` в глобальном модуле после переезда типа в
   `vw.core` — модульные сущности так объявлять нельзя.

## Метрики

Полная сборка проекта (Release, MSVC, Ninja): **22,3 с**, 37 TU. До миграции
было 17,7 с — рост объясняется появлением модульных юнитов и сканирования; это в
пределах цели «не хуже базлайна ×1,2».

Инкрементальная пересборка:

| Правка | Пересобрано TU | Время |
|---|---|---|
| реализация `math.cpp` (1067 строк) | **1** | 2,2 с |
| реализация `blocks.cpp` | **1** | 4,3 с |
| интерфейс `math.cppm` | 28 | 18,2 с |
| интерфейс `blocks.cppm` | 29 | 19,0 с |

Для сравнения, header-only базлайн из M0: правка `core/types.h` пересобирала
16 TU из 17, правка `core/block_registry.inl.h` — 8 из 17. Реализация,
переехавшая в имплементационный юнит, теперь стоит ровно один TU.

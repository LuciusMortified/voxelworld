# M5. `vw.gfx` + миграция на Vulkan-Hpp

Статус: **выполнено частично**. Рендер целиком переехал в модуль `vw.gfx` и
целиком переведён на `vk::`/`import vulkan`. Не сделаны два пункта приёмки —
`deletion_queue` (D4) и замер FPS; разбор в конце.

Фаза сознательно разделена надвое вопреки плану, который требовал делать
конверсию в модуль и миграцию на Vulkan-Hpp одним проходом:

- **M5.1** — механический переезд `engine/include/vw/gfx/**` → `engine/gfx/src/**`
  с сохранением C API. Не трогает ни одной строки с `vkCreate*`, скриптуется,
  проверяется независимо.
- **M5.2** — собственно `vk::`. ~215 мест, каждое требует решения.

Разделение дало зелёный проверенный базлайн перед правкой вызовов. Цена —
`:resource`, `:render` и `:renderer` пришлось переписывать дважды в части
объявлений; это дешевле, чем отлаживать 10 тысяч строк в одной красной зоне.

## Структура модуля

| Партиция | Содержимое | Экспортируется |
|----------|------------|----------------|
| `:camera` | camera, fps/free/third-person контроллеры, player input | да |
| `:resource` | buffer и наследники, staging, mesh(+pool), palette, light, combined_buffer(+pool), shader, debug_primitive | да |
| `:render` | vulkan_context, shadow_map, cull_pipeline | да |
| `:renderer` | renderer | да |
| `:engine` | app, engine, debug_window | да |
| `:logging` | обёртка над `vw::log` | нет |
| `:vk` | `vk_must`, `vk_panic` | нет |

`import vulkan;` стоит в `:vk`, `:resource`, `:render`, `:renderer` и в
имплементационных юнитах — **везде без `export`**. Поэтому потребитель `vw.gfx`
не может назвать ни одного `vk::`-имени, хотя определения ему достижимы
(reachable) — этого достаточно, чтобы посчитать размер `renderer` и остальных
классов.

## Окружение: модуль `vulkan` берётся из vcpkg, не из SDK

Установленный SDK 1.4.313.2 отстаёт от переименования модуля и объявляет
`export module vulkan_hpp;`. Сборка при этом уже использует vcpkg-порт
**vulkan-headers 1.4.350.1** (он приходит транзитивно через
`imgui[vulkan-binding]`), где объявлено `export module vulkan;`, — и
`Vulkan_INCLUDE_DIR` указывает именно туда. Отдельно добавлять зависимость в
`vcpkg.json` не потребовалось; отчёт M0 в этой части подтвердился полностью.

Раскладка `.cppm` в 1.4.350.1 отличается от версии в SDK принципиально:
`vulkan.hpp` включается **внутри пурвью модуля**, а не в global module fragment.
Отсюда два следствия, на которые опирается вся фаза: `VULKAN_HPP_EXPORT`
разворачивается в `export`, поэтому `vk::detail::defaultDispatchLoaderDynamic`
и `vk::ResultValue` действительно экспортируются; и сам `.cppm` определяет
`VULKAN_HPP_CXX_MODULE`, поэтому хранилище диспетчера принадлежит модулю и
макрос `VULKAN_HPP_DEFAULT_DISPATCH_LOADER_DYNAMIC_STORAGE` в наших TU не нужен.

## Решение сверх плана: `VULKAN_HPP_USE_STD_EXPECTED`

К пяти макросам конфигурации на таргете `VulkanHppModule` добавлен шестой. Без
него падающий вызов возвращает `vk::ResultValue<T>` — тип, который надо
называть в сигнатуре хелпера. С ним возвращается `std::expected<T, vk::Result>`:
стандартный тип, монадические операции, и `vk_must` сводится к проверке
`has_value()`. D3 и так построен на `std::expected` — макрос просто убирает
второй параллельный result-тип.

`vk::ResultValue` при этом не исчезает: вызовы с несколькими кодами успеха
(создание пайплайнов) продолжают возвращать его. Для них у `vk_must` есть
перегрузка, отобранная по структуре (`requires { rv.result; rv.value; }`), —
так имя биндингового типа не попадает в наш код вообще.

## Диспетчер (D6)

Три шага ровно там, где предписывал план, и `vk::detail` упоминается ровно в
одном файле за собственным аксессором:

```cpp
// vulkan_context.cpp
auto dispatcher() -> vk::detail::DispatchLoaderDynamic& {
    return vk::detail::defaultDispatchLoaderDynamic;
}
```

`dispatcher().init()` без аргументов сам находит `vulkan-1.dll`, затем
`init(instance_)` и `init(device_)`. Из-за этого `vw_gfx` больше **не линкует**
`vulkan-1.lib` и не получает `${Vulkan_INCLUDE_DIRS}`: связь с биндингом —
только `VulkanHppModule`. `vw_platform` свою ссылку сохраняет: `glfwCreateWindowSurface`
работает с C API.

Первая же выгода от динамического диспетчера — минус два ручных
`vkGetInstanceProcAddr`-бойлерплейта: `create_debug_utils_messenger_ext` и
`destroy_debug_utils_messenger_ext` (28 строк) заменились на прямые
`instance_.createDebugUtilsMessengerEXT(...)` / `destroyDebugUtilsMessengerEXT(...)`,
а запрос VRAM в `engine.cpp` — с 30 строк поиска
`vkGetPhysicalDeviceMemoryProperties2` до одного `getMemoryProperties2` со
`StructureChain`.

## Ноль C API — с четырьмя исключениями по D8

`grep -rn 'vkCreate\|vkCmd\|Vk[A-Z]\|VK_[A-Z]' engine/gfx/src/` даёт четыре
строки, все в `renderer.cpp` и все на границе с бэкендом imgui, который принимает
только C-типы: `init_info.ApiVersion`, `CheckVkResultFn`, `static_cast<VkSampleCountFlagBits>`
и `static_cast<VkImageLayout>`. Ровно этот случай D8 и описывает.

Ни один файл модуля больше не включает `<vulkan/vulkan.h>`. `vulkan_context.cpp`
обошёлся без него благодаря трём находкам: `vk::PFN_DebugUtilsMessengerCallbackEXT`
принимает vk-типы, а не C-типы, поэтому колбэк валидации написан на `vk::`;
имена расширений есть как `vk::KHRSwapchainExtensionName` и соседи; а `VkSurfaceKHR`
для передачи сюрфейса из `vw.platform` называется через `vk::SurfaceKHR::NativeType`.
Из `engine/include/vw/gfx/detail/module_prelude.h` Vulkan-заголовок убран.

## Найденный дефект: слои валидации были выключены в Debug

`vulkan_context.cpp` запрашивал `VK_LAYER_KHRONOS_validation` под `#ifdef NDEBUG`,
то есть **только в Release**, — а debug-мессенджер создавался под `#ifndef NDEBUG`,
то есть только в Debug. Ни одна конфигурация не имела обеих половин: в Debug
слои не грузились, в Release некому было доставлять сообщения.

Из этого следует, что проверка «валидационные слои чистые» в отчёте M5.1
ничего не доказывала: сообщений не было, потому что не было слоёв. Условие
исправлено на `#ifndef NDEBUG`, и проверка этой фазы уже с зубами — загрузка
слоя подтверждена отдельно, `VK_LOADER_DEBUG=layer` печатает
`Insert instance layer "VK_LAYER_KHRONOS_validation"`.

## Interop C ↔ Hpp: план был прав наполовину

Утверждение плана «мигрировать можно партицию за партицией при живом рендере»
верно только для хэндлов. По факту:

- **хэндлы** (`vk::Buffer` ↔ `VkBuffer`) конвертируются неявно в обе стороны —
  на x64 включён `VULKAN_HPP_TYPESAFE_CONVERSION`;
- **структуры** конвертируются неявно в C-аналог (`operator VkFoo const&`),
  но не обратно;
- **enum'ы** не конвертируются никак: `vk::Format` — scoped enum, нужен
  `static_cast`;
- **контейнеры** не конвертируются вовсе: `std::vector<vk::SurfaceFormatKHR>`
  и `std::vector<VkSurfaceFormatKHR>` — несвязанные типы.

Практический вывод: как только у класса меняется хоть один enum- или
struct-член интерфейса, все его потребители обязаны мигрировать в том же
коммите. Попытка конвертировать `vulkan_context` в одиночку немедленно сломала
`renderer.cpp` на `swapchain_support_details`. Поэтому M5.2 сделана сплошным
проходом, а не «партиция за партицией», как предполагал план.

## Как это делалось

Таблица соответствий C-констант и `vk::`-перечислений не писалась руками, а
извлекалась из `vulkan_enums.hpp` (4290 пар `eXxx = VK_YYY`). Проверка покрытия
показала 157 использованных констант, ноль неоднозначностей и восемь
неотображаемых — все они оказались строковыми макросами имён расширений и
фрагментами строковых литералов. Подстановка шла от длинных имён к коротким,
чтобы префиксы не съедали друг друга. Вызовы (`vkCreateX`, `vkCmdX`, парные
count+pointer) конвертировались отдельными шаблонными преобразованиями с
разбором скобок, остаток — вручную по ошибкам компилятора.

Designated initializers (D5) применены там, где блок и так переписывался
целиком. Массовую замену «поле за полем» на designated init в `renderer.cpp` я
не делал: у `vk::`-структур `sType` — инициализатор члена по умолчанию, поэтому
старый стиль столь же безопасен, а диффа он добавил бы вдвое.

## Что осталось не сделано

- **`deletion_queue` (D4)** — не реализована. Критерий «нет `vkDeviceWaitIdle`
  в путях освобождения ресурсов» формально выполнен: `wait_idle` остался в трёх
  местах — деструктор `renderer`, `engine::shutdown` и `recreate_swapchain`;
  первые два это shutdown, третий — ресайз, который в любом случае требует
  дренажа кадров. Но исходная задача D4 шире: `combined_buffer` при расширении
  уничтожает GPU-буферы без оглядки на кадры в полёте. Валидация на прогоне
  молчит, значит на практике не стреляет, но гарантии нет. Это отдельная
  задача, а не хвост миграции.
- **FPS эталонной сцены** — не измерен. Движок считает `engine_stats::fps`, но
  наружу его отдаёт только debug-окно ImGui; сравнить с базлайном без правки
  кода нельзя, а базлайн M0 численно и не зафиксирован. Критерий остаётся
  открытым.
- **Гигиена интерфейсов до буквы M5.6** — `:resource` и `:render` остались
  экспортируемыми, поэтому vk-типы формально присутствуют в интерфейсе
  экспортируемых классов (как типы приватных членов). Практический эффект
  правила уже достигнут: назвать `vk::`-имя снаружи `vw.gfx` нельзя. Перевод
  партиций во внутренние упирается в `gfx::shadow_map::cascade_count`, который
  использует Sculptor.
- **Линт интерфейсной гигиены в CI** — CI ещё нет, он заводится в M6.

## Проверки

- Матрица {MSVC, Clang} × {Debug, Release} — по 140/140.
- Headless (`-DVW_BUILD_GFX=OFF -DVW_BUILD_APPS=OFF`) — 140/140.
- Sculptor, Debug, слои валидации подтверждённо загружены: запуск, генерация
  мира, четыре ресайза окна, сворачивание и разворачивание (путь свапчейна
  нулевого размера), выход — код 0, **ноль** сообщений валидации.
  Полёт и правки вокселей автоматизировать не удалось: они требуют ввода.
- Полная чистая пересборка Release — 24,8 с (268 шагов ninja вместе с очисткой).
- Правка `renderer.cpp` — 1 TU, 8,7 с. В M5.1 та же правка занимала 3,6 с:
  разница — цена `import vulkan` в этом TU. BMI биндинга большой, и его платит
  каждый юнит, который его импортирует.

## Изменения вне рендера

`uint32_t` и родня заменены на типы проекта (`uint32`, `int32`) во всём
`engine/gfx/src`. Формально это следование правилу CLAUDE.md, фактически —
требование Clang: `import std;` даёт `std::uint32_t`, но не глобальный
`::uint32_t`, а текстовые `<cstdint>` из global module fragment исчезли вместе
с C-заголовками. MSVC это прощал, Clang нет.

Там, где `import std;` не покрывает макросы, C-заголовки вернулись в global
module fragment точечно: `<cstddef>` для `offsetof` в `mesh.cpp` и
`debug_primitive.cpp`, `<cassert>` для `assert` в `staging_buffer.cpp`.
`UINT32_MAX`/`UINT64_MAX` заменены на `std::numeric_limits`.

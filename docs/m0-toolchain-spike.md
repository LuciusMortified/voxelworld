# M0 — отчёт тулчейн-спайка

**Дата:** 2026-08-01 · **Ветка:** `modules-migration` · **Статус:** приёмка пройдена

Спайк выполнен на изолированном скелете `spike/`, движок не тронут. Матрица
{MSVC, Clang} × {Debug, Release} зелёная: `import std`, именованные модули с
партициями, имплементационный юнит, Catch2 поверх модулей, модуль `vulkan` с
рабочим динамическим диспетчером.

## Находки

### 1. libc++ под Windows не нужен — риск №1 снят

План закладывал фолбэк «Clang живёт на libc++» на случай, если `import std` не
заработает на связке clang + MS STL. Фолбэк не потребовался: Clang собирает
майкрософтовский `std.ixx` без единой ошибки, и потребитель с `import std;`
компилируется, линкуется и запускается. libc++ в Windows-сборках LLVM
отсутствует физически, так что снятие этого требования убирает и всю возню с
кастомным vcpkg-триплетом под другой ABI.

### 2. Clang-ветка обязана идти через `clang++`, а не `clang-cl`

CMake включает сканирование графа импортов для Clang только при GNU-подобном
фронтенде (`Modules/Compiler/Clang-CXX.cmake:29`). С `clang-cl` конфигурация
падает на «the compiler does not provide a way to discover the import graph
dependencies», причём наличие `clang-scan-deps` в PATH ничего не меняет.
`clang++` на Windows остаётся в MSVC-ABI и продолжает использовать MS STL —
совместимость с vcpkg-зависимостями сохраняется.

### 3. Модуль `std` для Clang собираем сами

Штатный `CMAKE_CXX_MODULE_STD` поддерживает только MSVC (через `std.ixx`) и
Clang с libc++/libstdc++ (`Modules/Compiler/Clang-CXX-CXXImportStd.cmake`). Для
Clang + MS STL CMake отказывается. Обход — обычный модульный таргет из того же
`std.ixx`, см. `spike/std/CMakeLists.txt`. Никакой экзотики: это штатный
`FILE_SET CXX_MODULES`, просто источник берётся из каталога MSVC.

### 4. Имя модуля Vulkan-Hpp: план был прав, отставало окружение

Модуль переименован `vulkan_hpp` → `vulkan` в **Vulkan-Headers 1.4.334**.
Установленные версии (vcpkg 1.4.309, SDK 1.4.313) были старше переименования,
из-за чего `import vulkan;` из плана не находился. Лечится обновлением, а не
правкой кода: после подъёма baseline vcpkg отдаёт 1.4.350.1, где объявлено
`export module vulkan;`. Начиная с той же версии модуль делает `export import
std;` — то есть `import std` для него обязателен, что у нас уже выполнено.

### 5. В наших исходниках макросы Vulkan-Hpp не нужны вообще

Конфигурация (`VULKAN_HPP_NO_EXCEPTIONS`, `NO_CONSTRUCTORS`, `NO_SMART_HANDLE`,
`DISPATCH_LOADER_DYNAMIC=1`) задаётся один раз через `target_compile_definitions`
на таргете модуля и в код не попадает. `VULKAN_HPP_DEFAULT_DISPATCHER` был
единственным макросом, просачивавшимся в исходники, — он всего лишь алиас на
`vk::detail::defaultDispatchLoaderDynamic`, которая экспортируется модулем.
Итоговый smoke-тест не содержит ни одного макроса и ни одного `#include`:
только `import std;` и `import vulkan;`.

### 6. Хранилище диспетчера принадлежит модулю

При `VULKAN_HPP_CXX_MODULE` переменная `defaultDispatchLoaderDynamic`
определяется внутри модуля (`vulkan.hpp:26855`). Макрос
`VULKAN_HPP_DEFAULT_DISPATCH_LOADER_DYNAMIC_STORAGE` в потребителе даёт
`LNK2005: уже определён`. Бутстрап упрощается до безаргументного `init()`,
который сам находит `vulkan-1.dll` — C-заголовки для этого не требуются.

Общее правило при этом остаётся в силе: C-декларации живут в global module
fragment и наружу не экспортируются. Для M4 (создание `VkSurfaceKHR` рядом с
GLFW) это по-прежнему означает явный `#include <vulkan/vulkan.h>` в
имплементационном юните.

### 7. Гейт `import std` в CMake 4.1

`CMAKE_EXPERIMENTAL_CXX_IMPORT_STD` = `d0edc3af-4c50-42ea-a356-e2862fe7a444`.
Значение привязано к версии CMake и будет меняться при обновлении.

### 8. Ловушка двух деревьев `vcpkg_installed`

Тулчейн vcpkg в манифестном режиме ставит зависимости в
`${CMAKE_BINARY_DIR}/vcpkg_installed`, то есть **в каталог сборки**. В корне
исходников лежит одноимённый каталог — устаревший артефакт (gitignore, не
отслеживается), и именно он ввёл в заблуждение на старте: спайк собирался с
заголовками 1.4.309, хотя зависимости уже обновились. Спайк переведён на
тулчейн с `VCPKG_MANIFEST_DIR`, на корневой каталог больше ничего не ссылается;
его можно удалить.

### 9. imgui 1.92 сломал инициализацию Vulkan-бэкенда

`RenderPass`, `Subpass` и `MSAASamples` убраны из `ImGui_ImplVulkan_InitInfo` и
переехали в подструктуру `PipelineInfoMain`; добавлено обязательное поле
`ApiVersion`. Правка механическая, сделана в `renderer.inl.h`. API шрифтов,
поменявшийся в 1.92 сильнее всего, проект не использует.

## Метрики базлайна

Спайк, все конфигурации зелёные (4/4 теста), секунды:

| Конфигурация | configure | полная | правка интерфейса | правка реализации |
|---|---|---|---|---|
| msvc-release | 7,80 | 9,73 | 1,98 | 1,52 |
| msvc-debug | 7,34 | 9,51 | 1,96 | 1,31 |
| clang-release | 8,03 | 11,39 | 1,85 | 1,72 |
| clang-debug | 7,91 | 8,24 | 1,83 | 1,36 |

`configure` включает проверку манифеста vcpkg, отсюда ~7–8 с.

На скелете абсолютные времена малы и в них доминируют старт ninja и линковка,
поэтому показателен объём пересборки (msvc-release, реальные сборки — `ninja -n`
завышает, так как не учитывает `restat`):

| Правка | Пересобрано TU |
|---|---|
| реализация (`math.cpp`) | **1** + линковка; потребители не тронуты |
| интерфейсная партиция (`math.cppm`) | 5 — партиция, первичный интерфейс, имплементационный юнит и два прямых потребителя (`types.cppm` не тронут) |

Текущий header-only движок, MSVC Release + Ninja — это база для сравнения в M6:

| Сценарий | Время | Пересобрано TU |
|---|---|---|
| полная сборка тестов | 4,15 с | 17 из 17 |
| правка `core/types.h` | 4,08 с | **16 из 17 (94%)** |
| правка `core/block_registry.inl.h` | 3,79 с | 8 из 17 (47%) |
| полная сборка проекта (apps + tests) | 17,7 с | — |

Главная цифра: сегодня правка одной *реализации* в `.inl.h` пересобирает
половину проекта, а правка заголовка — практически весь. В модульном варианте
правка реализации стоит ровно один TU. Это и есть выигрыш, который M6 должен
подтвердить на боевом коде.

## Остальные точки риска

- **BMI-гигиена** — проверено: смена флага компиляции корректно инвалидирует
  модули (10 TU пересобраны, сборка зелёная, никаких ошибок про устаревший BMI).
- **clangd** — по модульному коду не работает: `Module 'std' not found`,
  `Module 'vulkan' not found`, при том что сборка зелёная. Принято как известное
  ограничение, истина — сборка.
- **ccache/sccache** — не установлены, риск неактуален.

## Что сделано в репозитории

- `spike/` — скелет, воспроизводящий все элементы целевой сборки. Остаётся как
  эталон CMake-рецепта для M1 и удаляется, когда боевой `vw_core` встанет на его
  место.
- `cmake_minimum_required` поднят до 4.0 в корне, `engine/`, `apps/`, `tests/`.
- baseline vcpkg поднят до `39344dff01c5a5a0134caf2624cdd492f05d30ea`;
  зависимости обновились до vulkan-headers 1.4.350.1, imgui 1.92.8,
  catch2 3.15.3, spdlog 1.17.0 (последний будет удалён в M1).
- `renderer.inl.h` — инициализация imgui приведена к новому API.
- Проект собирается целиком, все 127 существующих тестов зелёные.

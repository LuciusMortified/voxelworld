# Хвосты M5. План

Два незакрытых пункта приёмки M5 (`docs/m5-vw-gfx.md`, раздел «Что осталось не
сделано»): очередь отложенной деструкции (D4) и замер кадрового времени.
Ни то, ни другое не является хвостом миграции в буквальном смысле — это
самостоятельные задачи, которые миграция вскрыла и оставила задокументированными.

Порядок обратный тому, в котором они перечислены в отчёте: **сначала замер,
потом D4**. Обоснование — в разделе «Порядок».

## Исходное состояние

### Где уничтожаются живые GPU-ресурсы

Ровно в одном месте вне shutdown и ресайза свапчейна — при расширении буферов
`combined_buffer`:

| Место | Что гибнет |
|---|---|
| `combined_buffer.cpp:455-456` | `vertex_buffer_`, `index_buffer_` |
| `combined_buffer.cpp:516-520` | пять instance-буферов |
| `combined_buffer.cpp:522-531` | `culled_indirect_buffer_`, `count_buffer_` |

Оба `expand_*` вызываются из горячего пути: `allocate` (`combined_buffer.cpp:121`)
и `allocate_mesh` (`:217`), а те — из `combined_buffer_pool::update`, который
renderer зовёт на `renderer.cpp:319`, **после** `command_buffers_[…].begin()` на
`:309`. Расширение происходит в середине записи кадрового командного буфера.

### Почему валидация молчит

Не потому, что путь безопасен. `buffer::copy_to_buffer` заканчивается полным
дренажем графической очереди:

```cpp
// engine/gfx/src/buffer.cpp:127-132
const vk::Queue queue = context_->get_graphics_queue();
vk_must(queue.submit(...), "submit buffer copy");
vk_must(queue.waitIdle(), "wait for buffer copy");
```

К моменту `std::move` все ранее отправленные кадры завершены, поэтому старый
буфер действительно никем не используется. Корректность держится на побочном
эффекте копирования, а не на управлении временем жизни.

Три следствия:

1. `culled_indirect_buffer_` и `count_buffer_` (`:522-531`) пересоздаются
   **без копирования вовсе** — собственного `waitIdle` у них нет. Они безопасны
   лишь потому, что выше по той же функции отработали пять чужих
   `copy_to_buffer`. Убрать любое из этих копирований — получить
   use-after-free, который ничем себя не проявит.
2. Дренаж очереди посреди кадра — гарантированный провал по времени кадра ровно
   в тот момент, когда подгружается новая геометрия.
3. Отложенные записи staging при расширении не теряются: `replace_buffer`
   (`staging_buffer.cpp:113-118`) перенаправляет их на новый хэндл. Этот
   механизм нужен и после D4, трогать его не нужно.

## Задача 1. Замер кадрового времени — **выполнено**

Числа и способ их снять — `docs/frame-time-baseline.md`. Отклонения от плана
ниже: три штуки, и одно из них вскрыло дефект.

**Готовность сцены пришлось сделать залипающей.** План говорил «замер стартует
после того, как pending обнулился». Для `parked` это работает, для облёта —
нет: движущаяся камера не даёт стримингу закончиться никогда, и первый прогон
`flythrough` просто не завершился. Правильная формулировка: готовность гейтит
только начальную прогрузку и после срабатывания залипает, а стриминг во время
полёта — часть замера, ради которой этот режим и нужен.

**Камеру пришлось вести по собственному счётчику**, а не по номеру кадра
движка: номер кадра на момент готовности зависит от того, сколько заняла
прогрузка, то есть от машины. Траектория обязана считаться от нуля, взятого в
момент старта замера.

**Завершение бенчмарка вскрыло падение на выходе** (0xC0000005), и оно не
имеет отношения к замеру. `renderer::~renderer` останавливает потоки генерации
мешей первой же строкой (`renderer.cpp:92`), но `renderer_` объявлен в `engine`
раньше `world_` и потому уничтожается **позже** него: рабочие потоки переживают
мир, чьи страницы моделей читают. Руками это почти не поймать — надо выйти из
приложения ровно в момент активной подгрузки; бенчмарк делает это каждый
прогон. Лечится одной строкой в `engine::shutdown`, которая гасит потоки до
разрушения чего бы то ни было. `parked` при этом не падал никогда: очередь
пуста, гонки нет.

### Что было

`engine_stats` (`engine.cppm:112-123`) хранит **одно последнее значение**:
`stats_.frame_ms` и `stats_.fps = 1000.0f / frame_ms` считаются в
`update_stats` (`engine.cpp:147-154`) на каждом кадре, перезаписывая предыдущее.
Разбивка по стадиям есть и на уровне движка (`world_update_ms`, `renderer_ms`,
`end_frame_ms`, …), и на уровне рендера — `render_timing_stats`
(`renderer.cppm:85-95`: shadow map, buffer pool, compute cull, проходы).
Материала достаточно; отсутствует накопление и вывод.

Наружу число уходит только через ImGui: гистограмма `fps_bucket_*` в
`debug_window` (`engine.cppm:100-103`). Прочитать его без глаз на экране нельзя.

### Шаг 1.1 — накопитель

Новый тип в партиции `:engine`, рядом с `engine_stats`:

```cpp
struct frame_sample {
    float32 frame_ms      = 0.0f;
    engine_stats engine{};
    render_timing_stats render{};
};

class frame_recorder final {
public:
    explicit frame_recorder(uint32 capacity);

    auto record(const frame_sample& sample) -> void;
    [[nodiscard]] auto percentile(float32 q) const -> float32;
    [[nodiscard]] auto report() const -> std::string;

private:
    std::vector<frame_sample> samples_;
};
```

Хранить сэмплы целиком, а не только `frame_ms`: перцентили по стадиям нужны,
чтобы отличить провал в `buffer_pool_update_ms` (расширение) от провала в
`world_update_ms` (стриминг чанков). `report()` считает p50/p95/p99/max по
`frame_ms` и p50/p99 по каждой стадии.

Место — `:engine`, а не `debug_window`: последний привязан к ImGui, а отчёт
должен работать в прогоне без окна отладки.

### Шаг 1.2 — вывод без ImGui

Конфигурация через конструктор (двухфазной инициализации не заводим):

```cpp
struct bench_config {
    uint32 warmup_frames  = 0;   // 0 — режим выключен
    uint32 measure_frames = 0;
    std::string_view report_path{};
};

engine(int32 width, int32 height, std::string_view title, bench_config bench = {});
```

`main_loop` (`engine.cpp:105-123`) считает кадры: первые `warmup_frames`
выбрасываются, следующие `measure_frames` пишутся в `frame_recorder`, затем
отчёт уходит в лог и в `report_path`, и цикл ставит `running_ = false`.

Разбор argv — в `main()` приложения, не в движке.

В отчёт обязательно попадают: имя GPU, конфигурация сборки, **выбранный режим
представления** и `MAX_FRAMES_IN_FLIGHT`. Про режим представления отдельно:
`choose_swap_present_mode` (`renderer.cpp:1718-1727`) берёт Mailbox если он
доступен, иначе Fifo. На машине с Fifo бенчмарк молча упрётся в частоту
монитора и покажет ровные 16,6 мс — это надо видеть в отчёте, а не выяснять
задним числом.

### Шаг 1.3 — сцена

Кандидат — `apps/test_world_grid`. Генерация детерминирована: сид фиксирован
(`terrain.cppm:120`, `seed = 42`). Но `chunk_loader` крутит до четырёх рабочих
потоков (`terrain.cpp:13`) и отдаёт готовые колонки через очередь, поэтому
**момент** прихода геометрии от прогона к прогону плавает. Отсюда два режима, и
оба нужны:

- **`static`** — камера припаркована в фиксированной точке; замер стартует
  после того, как `world_grid_system::get_stats().pending_count` и
  `mesh_pool::get_pending_count()` оба обнулились. Низкая дисперсия, это
  сравнимое между сборками число.
- **`flythrough`** — камера на рельсах: путь считается от **номера кадра**, а не
  от `delta_time`, и сам `delta_time` фиксируется (1/60), иначе мир обновляется
  по-разному. Стриминг входит в замер. Здесь и видны p99-провалы — те самые, где
  сидит `waitIdle` из расширения.

`camera_controller_->update(delta_time)` в bench-режиме подменяется на
вычисление позиции по номеру кадра; клавиатура и мышь отключаются.

### Чего в этой задаче не будет

**Сравнения с базлайном M0 не будет.** Число до миграции численно не
зафиксировано, а pre-migration дерево (`12969f9`, последний коммит перед
`0567188 docs: add modules migration plan`) ничего не печатает. Получить его
можно только так: `git worktree` на `12969f9`, поверх — некоммиченный патч с
обвязкой замера, плюс разбор vcpkg-версий той эпохи. Это отдельные полдня ради
числа, которое почти наверняка ляжет в шум: модуляризация не меняет
генерируемый код, а Vulkan-Hpp — тонкая обёртка, где единственная реальная
разница это косвенный вызов через динамический диспетчер (D6).

Предлагаю зафиксировать сегодняшнее число как базлайн и честно исправить
`docs/m5-vw-gfx.md`: критерий «не хуже базлайна M0» непроверяем, потому что
базлайна не существует. Если число «до» всё-таки понадобится — это отдельная
задача после.

### Приёмка задачи 1 — пройдена

- Два подряд прогона расходятся по p50 кадра на 0,15 % (`parked`) и 0,44 %
  (`flythrough`) при допуске 2 %.
- Отчёт содержит p50/p95/p99/max по кадру и по всем шестнадцати стадиям, режим
  представления, GPU, конфигурацию сборки и число кадров в полёте.
- Базлайн зафиксирован в `docs/frame-time-baseline.md`, формулировка в
  `docs/m5-vw-gfx.md` исправлена.
- 140/140 тестов, `scripts/lint_modules.py` — 0 нарушений.

## Задача 2. `deletion_queue` (D4)

### Отклонение от эскиза 5.4

Эскиз в `docs/modules-migration-plan.md:592-609` предлагает tagged union из
`{тип, uint64 handle}` и `defer(frame, vk::Buffer)` по типам. Предлагаю вместо
этого хранить **владеющие объекты**, а не хэндлы:

```cpp
// партиция :render, не экспортируется
class deletion_queue final {
public:
    auto retire(uint64 frame, std::unique_ptr<buffer> victim) -> void;
    auto collect(uint64 completed_frame) -> void;

private:
    struct entry {
        uint64 frame;
        std::unique_ptr<buffer> victim;
    };
    std::vector<entry> entries_;
};
```

Причины: уничтожение уже написано и уже корректно (`buffer::cleanup`,
`buffer.cpp:152-162` — снимает mapping, затем `destroyBuffer`, затем
`freeMemory`); tagged union это дублирует и добавляет третий путь освобождения
памяти. Единственный сегодняшний потребитель D4 держит ресурсы именно как
`std::unique_ptr<device_*_buffer>`. Расширение на образы и вьюхи — когда
появится место, которое их пересоздаёт в рантайме; сейчас такого нет.

### Коммит A — очередь, поведение не меняется — **сделано**

Два отклонения от того, что написано ниже.

**Партиция `:resource`, а не `:render`.** Граф партиций — `:camera` → `:resource`
→ `:render` → `:renderer`, а `combined_buffer` живёт в `:resource`. Очередь в
`:render` заставила бы `:resource` зависеть от `:render` и замкнула бы цикл,
который запрещён. Экспортируемой она при этом не стала.

**Номер кадра очередь хранит сама** (`set_frame`), вместо того чтобы принимать
его аргументом `retire`. Иначе кадр пришлось бы тащить через
`combined_buffer_pool` в `combined_buffer` и дальше в оба `expand_*` — четыре
уровня ради числа, которое известно ровно одному объекту, владеющему очередью.

Проверено прямой диагностикой: расширение mesh-буферов дало по два `retire`
на кадрах 352 и 457, расширение instance-набора — семь на кадре 542, и перед
каждым следующим расширением очередь пуста, то есть `collect` освобождает.
Числа бенчмарка совпали с базлайном, `buffer_pool_update` не сдвинулся.

Владелец — `renderer`: только он знает про кадры. `vulkan_context` не подходит,
он о кадрах не осведомлён. Передаётся в `combined_buffer` ссылкой в
конструкторе, ровно как уже передаётся `staging_buffer&`.

Нужен монотонный счётчик кадров в дополнение к `current_frame_`
(`renderer.cppm:326`), который циклится по модулю 2.

Сбор — в `begin_frame`, сразу после ожидания fence:

```cpp
// renderer.cpp:119-125, после waitForFences/resetFences
deletion_queue_.collect(frame_counter_ - MAX_FRAMES_IN_FLIGHT);
++frame_counter_;
```

Дополнительные fence'ы не нужны, и вот почему. `in_flight_fences_[current_frame_]`
сигналится сабмитом на `renderer.cpp:180`; `current_frame_` идёт по модулю
`MAX_FRAMES_IN_FLIGHT` (`:207`, значение 2 — `renderer.cppm:375`). Значит после
ожидания этого fence в начале кадра N кадр N−2 гарантированно завершён на GPU,
и всё, что было отправлено в отставку во время кадра N−2 или раньше, свободно.

В `expand_*` каждая подмена превращается из

```cpp
vertex_buffer_ = std::move(new_vertex_buffer);
```

в

```cpp
deletion_->retire(frame_counter_, std::exchange(vertex_buffer_, std::move(new_vertex_buffer)));
```

`waitIdle` в `copy_to_buffer` на этом коммите **не трогаем**. Поведение не
меняется вообще: старый буфер и так был свободен, теперь он просто освобождается
на два кадра позже. Коммит проверяем и безопасный сам по себе.

### Коммит B — убрать дренаж посреди кадра

Здесь очередь перестаёт быть страховкой и становится несущей.

Копию нужно записать в кадровый командный буфер вместо отдельного сабмита.
Протаскивать `vk::CommandBuffer` в `allocate`/`allocate_mesh` не требуется —
и это главное, что выяснилось при разборе. `staging_buffer` уже умеет
device→device копии:

- `pending_copy` хранит **и** `src`, **и** `dst` (`resource.cppm:348-352`), а
  `replace_buffer` (`staging_buffer.cpp:113-118`) патчит оба поля — для
  чисто staging-копий второе было бы бессмысленно;
- сортировка в `flush` (`staging_buffer.cpp:127-135`) отдельно выделяет случай
  `src != buffer_` и ставит такие копии **перед** staging-копиями. Это ровно тот
  порядок, который нужен расширению: сначала перелить старое содержимое в новый
  буфер, потом накатить свежие записи кадра.

То есть конструкция была рассчитана на этот сценарий, но им не пользуются.
Достаточно добавить в `staging_buffer` метод вида

```cpp
auto copy_buffer(vk::Buffer src, vk::DeviceSize src_offset,
                 vk::Buffer dst, vk::DeviceSize dst_offset, vk::DeviceSize size) -> void;
```

кладущий `pending_copy` с не-staging источником, и заменить им вызовы
`copy_to_buffer` в обоих `expand_*`. `buffer::copy_to_buffer` при этом остаётся
для путей вне кадра — либо удаляется, если таких не найдётся.

**Обязательная деталь:** `flush` сейчас не ставит ни одного барьера между
батчами (`staging_buffer.cpp:137-160`). Пока копия расширения шла отдельным
сабмитом с `waitIdle`, это было неважно. После переноса в общий командный буфер
между группой device→device и группой staging→device нужен
`vk::MemoryBarrier` (`eTransferWrite` → `eTransferWrite`, обе стадии
`eTransfer`): записи кадра могут попадать в те же смещения, что и только что
перелитая область.

`culled_indirect_buffer_` и `count_buffer_` (`:522-531`) после этого коммита
перестают зависеть от чужих копирований и начинают защищаться очередью явно.

### Проверка

Дефект воспроизводим, поэтому проверка строится от него, а не от «валидация
молчит»:

1. Сделать коммит B **без** коммита A на отдельной ветке-черновике.
2. Прогнать сцену, вызывающую расширение, с включёнными слоями (в M5 подтверждено,
   что они грузятся). Ожидаем `VUID-vkDestroyBuffer-buffer-00922`.
3. Вернуть коммит A — сообщение исчезает.

Сцена: расширение срабатывает при переходе через `default_instance_capacity_ = 64`
и `default_mesh_capacity_ = 32` (`resource.cppm:849-850`), то есть `test_world_grid`
доходит до него на первых же секундах полёта.

Дополнительно — прогон `flythrough` из задачи 1 до и после: p99 должен упасть,
p50 остаться на месте. Если p99 не изменился, значит расширение в этой сцене
случается реже, чем я думаю, и это тоже надо знать.

### Приёмка задачи 2

- В `copy_to_buffer`-путях нет `queue.waitIdle()`; `wait_idle` остаётся только в
  деструкторе `renderer`, `engine::shutdown` и `recreate_swapchain`.
- Слои валидации чистые на сценарии из M5 плюс полёт с расширением буферов.
- p99 `flythrough` улучшился, p50 не деградировал (числа в отчёт).
- Формулировка D4 в `docs/m5-vw-gfx.md` и `docs/m6-cleanup.md` закрыта.

## Порядок и оценка

Замер идёт первым, потому что коммит B — изменение производительности, и
снимать дренаж посреди кадра без возможности показать эффект бессмысленно:
мерить всё равно придётся, но тогда уже дважды.

| Шаг | Оценка |
|---|---|
| 1.1 + 1.2 накопитель и отчёт | 1–2 ч |
| 1.3 детерминированная сцена, два режима | ~2 ч |
| 2.A очередь, поведение не меняется | 2–3 ч |
| 2.B перенос копии в кадр, барьер, снятие `waitIdle` | ~3 ч |

Четыре коммита, каждый самостоятельно проверяем. Тесты движка (`core_tests`,
`ecs_tests`, `world_tests`) от этих правок не зависят — они headless, а весь
диф в `vw.gfx`, — но по правилу гоняются после каждого.

## Что этот план не закрывает

- **M5.6, гигиена интерфейсов.** `:resource` и `:render` остаются
  экспортируемыми из-за `gfx::shadow_map::cascade_count`, который использует
  Sculptor. Отдельная задача, к D4 отношения не имеет.
- **CI не прогонялся** (`docs/m6-cleanup.md:132`) — проверяется первым пушем, не
  кодом.
- `throw std::runtime_error` в `buffer::find_memory_type` (`buffer.cpp:149`) и
  в `begin_frame`/`end_frame` (`renderer.cpp:142`, `:199`) — по политике D3 это
  фатальный путь, то есть формально легально, но однообразия с `vk_must` там
  нет. Косметика, отдельно.
- Следы механической конверсии в `engine.cppm` (маркеры `// ---- from vw/gfx/…`
  и пустые блоки комментариев, `:189-199`). Тоже косметика.

# Voxelworld — план улучшений рендеринга и подготовки к сетевой RPG

**Версия:** 1.0 · **Дата:** 2026-08-01
**База:** `wiredreamer/voxelworld @ master` (120 коммитов, C++23/Vulkan, header-only engine)

Документ описывает восемь направлений работ (эпиков) с детальным дизайном, примерами кода в стиле проекта, точками интеграции в существующую кодовую базу, критериями приёмки и зависимостями. Порядок разделов = рекомендуемый порядок исполнения, карта зависимостей — в конце.

Обозначения путей даются относительно корня репозитория. Примеры кода — эскизы уровня "готово к адаптации": они используют реальные типы и сигнатуры проекта (`vw::uint32`, `block_id`, `page_entry`, trailing return types), но не претендуют на компилируемость без доработки.

# E1. Binary greedy meshing

## Проблема

Текущий `greedy_mesh_generator` (`engine/include/vw/gfx/resource/mesh.inl.h`) корректен алгоритмически, но реализация скалярная:

1. `detail::build_face_mask` заполняет маску слоя через `model::get_voxel()` по одному вокселю. Каждый вызов — разыменование `page_entry`, ветвление по `page_mode`, вычисление `local_index`. Для чанка 64³ это до 6 × 64 × 64 × 64 ≈ 1.5 млн вызовов на полный мешинг.
2. `merge_and_emit_rects` сравнивает `face_mask_cell` (структура `block_id` + `ao_key`) поэлементно при расширении прямоугольника — O(w·h) сравнений на квад.
3. Проверка `has_faces` — линейный проход по всей маске 64×64 после каждого слоя.
4. Граничные срезы `boundary_slice` хранятся как `std::vector<bool>` — обращение по биту через прокси-объект, нет пакетных операций.

Итог: мешинг чанка 64³ занимает миллисекунды. При беге игрока ремешатся десятки чанков в секунду; при сетевых правках от 8 игроков — ещё больше. Это главный кандидат на фризы.

## Целевой дизайн

Три уровня битовой обработки:

1. **Occupancy-столбцы**: весь чанк упаковывается в 64×64 столбцов `uint64` по каждой из трёх осей (или по одной оси + транспонирование). Заполнение идёт **из страниц напрямую**, минуя `get_voxel`: uniform-страница с непустым материалом записывает восемь бит `0xFF` в сегмент столбца одной операцией.
2. **Маски видимых граней**: `faces = col & ~(col >> 1)` для одной стороны, `col & ~(col << 1)` для противоположной, с подмешиванием граничного бита из соседнего чанка.
3. **Битовый greedy merge**: слой 64×64 — это 64 строки `uint64`; поиск начала рана — `std::countr_zero`, ширина рана — `countr_zero` инвертированной сдвинутой строки, расширение по высоте — сравнение битовых сегментов, а не поэлементное.

Материал и AO проверяются только для вокселей, попавших в маску видимых граней (обычно 1–5% объёма), — вот где остаётся скалярный код, и это нормально.

## Структуры данных

```cpp
// engine/include/vw/gfx/resource/binary_mesher.h
namespace vw::gfx {

struct chunk_occupancy {
    static constexpr int32 n = chunk<>::size;  // 64

    // столбцы по оси Y: y_cols[x * n + z], бит i = воксель (x, i, z) непуст
    std::array<uint64, n * n> y_cols;
    // аналогично для X и Z (либо получать транспонированием по месту)
    std::array<uint64, n * n> x_cols;
    std::array<uint64, n * n> z_cols;

    void clear() {
        y_cols.fill(0);
        x_cols.fill(0);
        z_cols.fill(0);
    }
};

struct face_masks {
    // 6 направлений × 64 слоя × 64 строки uint64
    std::array<std::array<uint64, 64 * 64>, 6> planes;
};

}  // namespace vw::gfx
```

Память: `chunk_occupancy` = 3 × 32 КБ = 96 КБ, `face_masks` = 6 × 32 КБ = 192 КБ. Обе структуры живут в `mesh_generation_storage` (уже есть) и переиспользуются потоком — аллокаций в горячем пути нет.

## Заполнение occupancy из страниц

Ключевой выигрыш — не читать воксели по одному. Страница 8³ в режиме `uniform` с материалом ≠ air даёт восемь установленных бит в 64 столбцах одним циклом; `empty` — пропускается целиком; только `sparse` требует чтения массива.

```cpp
// engine/include/vw/gfx/resource/binary_mesher.inl.h
inline void build_occupancy(chunk_occupancy& occ, const model& mdl) {
    constexpr int32 ps = model::page_size;  // 8
    occ.clear();

    for (int pz = 0; pz < mdl.pages_z(); pz++) {
        for (int py = 0; py < mdl.pages_y(); py++) {
            for (int px = 0; px < mdl.pages_x(); px++) {
                const auto mode = mdl.get_page_mode(px, py, pz);
                if (mode == page_mode::empty) {
                    continue;
                }

                const int32 bx = px * ps;
                const int32 by = py * ps;
                const int32 bz = pz * ps;

                if (mode == page_mode::uniform) {
                    // 8 бит [by, by+8) в 64 столбцах — одной маской
                    const uint64 seg = uint64{0xFF} << by;
                    for (int lz = 0; lz < ps; lz++) {
                        for (int lx = 0; lx < ps; lx++) {
                            occ.y_cols[(bx + lx) * 64 + (bz + lz)] |= seg;
                        }
                    }
                    continue;
                }

                // sparse: один проход по 512 вокселям страницы
                const auto* page = mdl.get_page(px, py, pz);
                for (int ly = 0; ly < ps; ly++) {
                    for (int lz = 0; lz < ps; lz++) {
                        for (int lx = 0; lx < ps; lx++) {
                            const auto& v = (*page)[local_index(lx, ly, lz)];
                            if (!v.is_empty()) {
                                occ.y_cols[(bx + lx) * 64 + (bz + lz)]
                                    |= uint64{1} << (by + ly);
                            }
                        }
                    }
                }
            }
        }
    }

    transpose_to_x_z(occ);  // битовое транспонирование 64×64, см. ниже
}
```

Транспонирование столбцов Y → X/Z делается стандартным алгоритмом битовой транспозиции 64×64 (Hacker's Delight, разделяй-и-властвуй по блокам 32/16/8/4/2/1) — ~6 проходов по массиву, без ветвлений. Альтернатива: строить три набора столбцов сразу в цикле заполнения; профилировать, что быстрее на ваших данных.

## Маски граней и границы чанков

```cpp
inline void build_face_masks(
    face_masks& fm, const chunk_occupancy& occ, const model& mdl
) {
    for (int i = 0; i < 64 * 64; i++) {
        const uint64 col = occ.y_cols[i];

        // бит соседа над верхней/под нижней границей чанка — из boundary_slice
        const uint64 above = boundary_bit_top(mdl, i);    // 0 или 1
        const uint64 below = boundary_bit_bottom(mdl, i);

        // грань +Y видна, если воксель есть, а над ним пусто
        fm.planes[face_pos_y][i] = col & ~((col >> 1) | (above << 63));
        fm.planes[face_neg_y][i] = col & ~((col << 1) | below);
    }
    // аналогично для x_cols / z_cols
}
```

Требование к E1: `boundary_slice` переводится с `std::vector<bool>` на `std::array<uint64, 64>` (битовая маска 64×64 на грань). Это отдельная задача внутри эпика — она упрощает и `set_boundary_slice`, и `is_boundary_solid`, и приведённый код выше.

## Битовый greedy merge

Маска граней говорит "здесь есть видимый квад", но сливать можно только квады с одинаковым материалом и AO. Двухфазный подход: битовый поиск кандидатов + скалярная проверка ключа только на кандидатах.

```cpp
struct quad_key {
    block_id id;
    uint8 ao_key;
    auto operator==(const quad_key&) const -> bool = default;
};

inline void merge_layer(
    std::span<uint64, 64> rows,               // маска слоя, будет обнуляться
    std::span<const quad_key, 64 * 64> keys,  // ключи вокселей слоя
    int face_direction, int layer,
    mesh_generation_storage& storage, const model& mdl,
    const block_registry& registry
) {
    for (int v = 0; v < 64; v++) {
        uint64 row = rows[v];
        while (row != 0) {
            const int u = std::countr_zero(row);
            const quad_key key = keys[v * 64 + u];

            // ширина: длина рана единиц с совпадающим ключом
            int w = 1;
            while (u + w < 64
                   && ((row >> (u + w)) & 1) != 0
                   && keys[v * 64 + u + w] == key) {
                w++;
            }
            const uint64 span = (w == 64) ? ~uint64{0} : ((uint64{1} << w) - 1) << u;

            // высота: расширяем, пока в следующей строке весь span установлен
            // и ключи совпадают
            int h = 1;
            while (v + h < 64 && (rows[v + h] & span) == span
                   && keys_match(keys, v + h, u, w, key)) {
                rows[v + h] &= ~span;
                h++;
            }

            rows[v] &= ~span;
            detail::emit_rect(
                storage, mdl, /*axes*/ face_axis_mapping(mdl, face_direction),
                face_direction, layer, u, v, w, h, key.id, registry
            );
            row = rows[v];
        }
    }
}
```

Массив `keys` заполняется одним проходом по установленным битам маски (итерация `countr_zero` + сброс младшего бита), с чтением материала из страницы и AO из occupancy-столбцов — AO по трём соседям угла считается битовыми выборками из `occ`, а не через `get_voxel`.

Замечание по AO: текущий `ao_key` в `face_mask_cell` уже агрегирует четыре угла — сохраните семантику, чтобы `emit_rect` и вершинный формат не менялись. E1 не трогает формат вершины.

## Интеграция

- `mesh_pool::gen_thread_function` (`mesh_pool.inl.h:180+`) вместо `greedy_mesh_generator::generate_mesh_data` вызывает `binary_mesh_generator::generate_mesh_data` с той же сигнатурой. Старый генератор остаётся как reference-реализация для дифф-тестов.
- `mesh_generation_storage` расширяется полями `chunk_occupancy` и `face_masks`.
- Для моделей, чей размер не кратен 64 (Sculptor-модели произвольных размеров), — фолбэк на старый генератор либо паддинг occupancy до 64. Рекомендация: binary-путь только для чанков `world_grid`, у которых размер фиксирован; Sculptor не критичен по скорости.

## Тесты и приёмка

- **Дифф-тест**: на наборе случайных и procedural-чанков множество эмитированных квадов (позиция, размер, материал, AO) старого и нового генератора совпадает с точностью до порядка. Оформить как `tests/mesh/binary_mesher_test.cpp` на Catch2 — в репозитории уже есть каркас тестов.
- **Бенчмарк**: `chunk 64³, поверхность perlin-рельефа` — целевое время ≤ 200 мкс на поток (Release, x64). Замер через существующий `completed_stats`.
- **Регрессия ремеша**: правка одного вокселя → полный цикл set_voxel → ремеш → аплоад ≤ 1 мс на CPU-стороне.

## Задачи эпика (черновая разбивка)

1. `boundary_slice` → битовые маски `uint64[64]`, адаптация `set_boundary_slice` / `is_boundary_solid`.
2. `chunk_occupancy` + заполнение из страниц + транспонирование, юнит-тесты на битовую корректность.
3. Маски граней с граничными битами, тесты на стыках чанков.
4. Битовый merge + сбор `quad_key`, дифф-тест против старого генератора.
5. AO из occupancy битовыми выборками, дифф-тест AO.
6. Подключение в `mesh_pool`, фолбэк для не-64³ моделей, бенчмарки, снятие старых логов.

# E2. Бюджеты стриминга, приоритеты и transfer queue

## Проблема

Сейчас пропускная способность стриминга ограничена константами в штуках:

- `mesh_pool.inl.h`: `max_meshes_per_frame = 4` — четыре готовых меша принимаются в кадр независимо от их размера (меш равнины и меш пещерного лабиринта отличаются на порядок).
- `world_grid.inl.h`: `max_columns_per_frame = 1` — одна колонка чанков в кадр. При беге со скоростью 10+ м/с фронт загрузки не успевает за игроком.
- Очереди `gen_queue_` / `completed_queue_` — FIFO: колонка за спиной игрока обрабатывается раньше колонки прямо по курсу, если встала в очередь раньше.
- Каждый меш-таск несёт `std::promise`/`std::future` — аллокация shared state, обход `pending_meshes_` с `wait_for(0s)` каждый кадр — O(n) по всем ожидающим таскам.
- Аплоад вершинных буферов идёт через staging на графической очереди — копирование конкурирует с рендером за GPU-время кадра.

## Целевой дизайн

### 2.1 Приоритетная очередь задач

Единый тип задачи стриминга с вычисляемым приоритетом; и генерация колонок, и мешинг, и аплоады сортируются одним правилом.

```cpp
// engine/include/vw/gfx/streaming/stream_priority.h
namespace vw::gfx {

struct stream_priority {
    // меньше = важнее
    float32 score;

    static auto compute(
        vec3i chunk_coord, vec3f camera_pos, vec3f camera_forward,
        uint32 lod_ring  // 0 до появления E4
    ) -> stream_priority {
        const vec3f center = chunk_center_world(chunk_coord);
        const vec3f to     = center - camera_pos;
        const float32 dist = length(to);

        // чанки по курсу движения важнее чанков за спиной
        const float32 facing = dot(normalize(to), camera_forward);  // [-1..1]
        const float32 facing_mul = facing > 0.0f ? 0.5f : 2.0f;

        // дальние LOD-кольца терпят
        const float32 ring_mul = 1.0f + static_cast<float32>(lod_ring);

        return {dist * facing_mul * ring_mul};
    }
};

}  // namespace vw::gfx
```

Очередь — бинарная куча под мьютексом достаточна (сотни элементов, операции короткие). Важная деталь: приоритет устаревает при движении камеры, поэтому раз в N кадров (например, 16) куча перестраивается с пересчётом score, либо используется ленивая схема: при извлечении элемент с сильно устаревшим score пересчитывается и возвращается в кучу.

### 2.2 Бюджет в миллисекундах и байтах

```cpp
struct frame_stream_budget {
    float32 integrate_ms   = 1.5f;   // CPU: принятие готовых колонок/мешей в мир
    uint32  upload_bytes   = 8u << 20;  // GPU: стейджинг-трафик за кадр
    uint32  min_items      = 1;      // защита от голодания при жирных элементах
};
```

`process_completed()` и `update_completed_meshes()` вместо счётчика штук ведут таймер (`std::chrono::steady_clock`) и счётчик байт; выход из цикла — по исчерпанию любого из бюджетов, но не раньше `min_items`. Статистика уже собирается в `completed_stats` — расширить полями `integrated_bytes`, `budget_exhausted_by`.

### 2.3 Замена future/promise на счётчики + очередь результатов

```cpp
// вместо pending_meshes_: unordered_map<identity, future<mesh>>
struct mesh_result {
    model_identity identity;
    mesh data;
};

class mesh_result_queue {
public:
    void push(mesh_result&& r) {
        std::scoped_lock lock(mutex_);
        results_.push_back(std::move(r));
    }

    // забрать всё разом, один захват мьютекса на кадр
    auto drain(std::vector<mesh_result>& out) -> void {
        std::scoped_lock lock(mutex_);
        out.insert(out.end(),
                   std::make_move_iterator(results_.begin()),
                   std::make_move_iterator(results_.end()));
        results_.clear();
    }

private:
    std::mutex mutex_;
    std::vector<mesh_result> results_;
};
```

Валидация актуальности (модель не изменилась, пока таск был в очереди) остаётся прежней — сравнение `model_identity` с текущим generation при интеграции результата. Отмена задач — тоже через generation: устаревший результат просто выбрасывается на этапе drain, отдельного механизма отмены не нужно.

### 2.4 Выделенная transfer-очередь

На дискретных GPU есть семейство очередей с только-`VK_QUEUE_TRANSFER_BIT` — это DMA-движки, копирующие параллельно графической работе. Использование:

```cpp
// vulkan_context: при выборе устройства
auto pick_transfer_family(std::span<const VkQueueFamilyProperties> families)
    -> std::optional<uint32> {
    // 1) семейство transfer-only (ни GRAPHICS, ни COMPUTE) — идеал
    for (uint32 i = 0; i < families.size(); i++) {
        const auto f = families[i].queueFlags;
        if ((f & VK_QUEUE_TRANSFER_BIT) != 0
            && (f & (VK_QUEUE_GRAPHICS_BIT | VK_QUEUE_COMPUTE_BIT)) == 0) {
            return i;
        }
    }
    // 2) фолбэк: любое отличное от графического
    // 3) фолбэк: та же очередь (интеграшки) — путь как сейчас
    return std::nullopt;
}
```

Схема кадра:

1. CPU пишет вершины/индексы готовых мешей в персистентно-замапленный ring-buffer стейджинга (host-visible, ёмкость = 2–3 × `upload_bytes`).
2. Транш `vkCmdCopyBuffer` сабмитится в transfer-очередь с timeline-семафором `transfer_done`.
3. Графическая очередь ждёт `transfer_done` (значение таймлайна) перед проходом, использующим новые регионы combined buffer.
4. Ownership transfer между семействами очередей: барьер `VK_SHARING_MODE_EXCLUSIVE` release/acquire, либо `VK_SHARING_MODE_CONCURRENT` на combined buffer (проще, чуть медленнее — приемлемый первый шаг).

Timeline-семафоры (`VK_KHR_timeline_semaphore`, core в 1.2) избавляют от пула бинарных семафоров: один монотонный счётчик, транши нумеруются, графика ждёт номер последнего затронувшего её транша.

### 2.5 Гистерезис загрузки/выгрузки

`world_grid_system::rebuild_active_set` держит один радиус. Для устранения дрожания на границе (колонка грузится-выгружается при осцилляции игрока) — два радиуса: `load_radius` и `unload_radius = load_radius + 2`. Колонка загружается при входе в первый, выгружается при выходе из второго.

## Интеграция

- `world_grid::request_column` / `gen_thread_function` — переход на приоритетную очередь (одна на генерацию, одна на мешинг — или общая с типом задачи).
- `mesh_pool` — удаление `pending_meshes_`, `update_completed_meshes` работает через `mesh_result_queue::drain` + бюджет.
- `staging_buffer` / `combined_buffer_pool` — ring-аллокатор и таймлайн-синхронизация; проверить, что существующий `staging_buffer` не пересоздаёт VkBuffer на каждый аплоад.
- `renderer` — ожидание таймлайна перед bind combined buffer.

## Приёмка

- Полёт над сгенерированным миром на скорости 50 вокс/с: p99 frametime не деградирует более чем на 15% относительно статичной камеры; очередь генерации не растёт неограниченно (равновесие).

# E3. Формат вокселя и палитры v2

## Проблема

Три ограничения текущего формата станут дорогими после появления сохранений и сети (форматы данных цементируются первыми):

1. **Палитра 256**: в вершине (`mesh.h`) `palette_index` занимает 8 бит (`data1[7:0]`), в `voxel.frag` — `palette[palette_idx & 0xFF]`. PRD обещает 8 биомов с рудами, растениями, структурами — 256 глобальных материалов закончатся.
2. **Воксель = только block_id**: нет места под пер-воксельное состояние — повреждение блока (частичная разрушаемость), уровень/поток воды, произрастание.
3. **Нет канала света**: флуд-филл освещение (sky + block light) — стандарт жанра для день/ночь и пещер; ему нужно 8 бит на воксель с теми же характеристиками разреженности, что у материалов.

## Целевой дизайн

### 3.1 Вершина v2

Сейчас в `data0` свободны биты [31:24], в `data1` — [31:18]. Перепаковка:

```cpp
// data0: pos.x[6:0] | pos.y[13:7] | pos.z[20:14] | normal_id[23:21] | light_sky[27:24] | light_block[31:28]
// data1: palette_index[13:0] | ao_c0..c3[21:14] | corner[23:22] | reserved[31:24]
```

- `palette_index` расширяется до 14 бит (16384 материалов — с запасом на годы).
- 8 бит света (4 sky + 4 block) кладутся в data0; до реализации E-light они заполняются константой 0xF (полная освещённость) — шейдер уже готов.
- Вершина остаётся 8 байт. `vertex::pack`, `get_attribute_descriptions`, `voxel.vert`, `shadow.vert` меняются согласованно — одна задача, один PR.

### 3.2 Каналы страниц

Обобщение `page_entry` на несколько каналов данных с одинаковой разреженной механикой:

```cpp
enum class page_channel : uint8 {
    material = 0,  // block_id — существующий канал
    state    = 1,  // uint8: повреждение/уровень воды/стадия роста
    light    = 2,  // uint8: sky[7:4] | block[3:0]
};

class model {
    // ...
    // pages_ становится per-channel; каналы state и light лениво
    // аллоцируются только если в модель хоть раз писали в этот канал
    std::array<std::vector<page_entry>, 3> channel_pages_;
    // page_pool расширяется типами страниц: page<voxel>, page<uint8>
};
```

Ключевые свойства:

- Канал, в который никогда не писали, не занимает памяти (вектор пуст, чтение возвращает default).
- `uniform`-режим работает и для света: полностью освещённая страница на поверхности — один `page_entry`, полностью тёмная в глубине — тоже.
- Мешер читает канал света при сборе `quad_key`/эмиссии вершин (свет пишется в вершину по 4 углам квада с интерполяцией, как AO).

### 3.3 Реестр блоков и стабильность идентификаторов

Для сохранений и сети `block_id::value` должен быть стабилен между версиями игры. В `block_registry` добавляется строковый неймспейс-ключ и таблица соответствия, сериализуемая в заголовок мира:

```cpp
struct block_def {
    std::string key;   // "vw:stone", "vw:oak_log"
    block_id id;       // runtime id, назначается при загрузке мира
    // ... цвет/палитра, флаги
};

// заголовок сохранения: массив key → persistent_id
// при загрузке строится ремап persistent_id → runtime block_id
```

Это стандартная схема (Minecraft datapacks, Vintage Story): на диске и в сети живут persistent id конкретного мира, в рантайме — плотные runtime id.

## Интеграция

- `vertex::pack` + оба вершинных шейдера + `palette_buffer` (размер буфера, индексация).
- `model` / `page_pool` — каналы; `set_voxel`/`get_voxel` получают перегрузки `set_state`, `get_light` и т.п.
- `vox`/`voxa` сериализаторы (`world/serializers/`) — версия формата в заголовке, каналы пишутся отдельными секциями (отсутствующий канал — отсутствующая секция).
- `block_registry` — ключи и ремап.

## Приёмка

- Мир, сохранённый до v2, загружается после v2 (миграционный путь или конвертер).
- 300+ материалов рендерятся корректно (тест палитры).
- Запись в канал state не аффектит модели, не использующие state (память, скорость мешинга).

## Задачи эпика

1. Вершина v2 + шейдеры + palette_buffer.
2. Каналы в model/page_pool с ленивой аллокацией.
3. Версионирование vox/voxa + секции каналов.
4. Строковые ключи блоков + ремап persistent/runtime.
5. (Опционально, после) флуд-филл свет как отдельный эпик поверх канала light.

# E4. LOD-кольца

## Проблема

Все загруженные чанки мешатся и рисуются в полном разрешении. Стоимость дальности обзора растёт кубически по вокселям и квадратично по чанкам: радиус 16 колонок — это уже ~1000 колонок × N чанков по вертикали. Для RPG с обзором «до горизонта» нужен LOD; в проекте есть заготовка — `voxel_scale` в `model` и `world_grid` — но нет ни даунсэмплинга, ни колец, ни бесшовных стыков.

## Целевой дизайн

### 4.1 Кольца

Мир делится на концентрические кольца вокруг игрока по расстоянию до колонки:

| Кольцо | Радиус (колонок) | voxel_scale | Чанк покрывает | Коллизии/правки |
|--------|------------------|-------------|----------------|-----------------|
| 0 | 0–8 | 1 | 64 м | да |
| 1 | 8–16 | 2 | 128 м | нет (только рендер) |
| 2 | 16–32 | 4 | 256 м | нет |
| 3 | 32–64 | 8 | 512 м | нет |

Число колец и радиусы — конфиг. Правки и физика существуют только в кольце 0; правка в зоне колец 1+ невозможна по дизайну (игрок далеко). Итоговая деталь: дальность 64 колонки = 4 км при том, что число рисуемых чанков растёт ~логарифмически на кольцо.

### 4.2 Даунсэмплинг

LOD N+1 строится из LOD N сверткой 2×2×2:

```cpp
// правило: непустой, если непустых >= порога; материал — мажоритарный
inline auto downsample_2x(const model& src, model& dst) -> void {
    for (int z = 0; z < dst.depth(); z++)
    for (int y = 0; y < dst.height(); y++)
    for (int x = 0; x < dst.width(); x++) {
        std::array<block_id, 8> ids{};
        int solid = 0;
        for (int i = 0; i < 8; i++) {
            const auto v = src.get_voxel(
                x * 2 + (i & 1), y * 2 + ((i >> 1) & 1), z * 2 + (i >> 2));
            if (!v.is_empty()) { ids[solid++] = v.id; }
        }
        if (solid >= 2) {  // порог 2/8 против "тающих" тонких структур
            dst.set_voxel(x, y, z, voxel{majority(ids, solid)});
        }
    }
}
```

Нюансы:

- Порог `>= 2` (а не `>= 4`) сохраняет тонкие стены и деревья; порог 1 делает даль «толстой». Значение — конфиг, подбирается визуально.
- Быстрый путь: если все 8 исходных страниц uniform с одним материалом — целевая страница uniform, без циклов. С E1-occupancy даунсэмплинг тоже делается битово: `dst_col = or_reduce(src_col_pairs)` + popcount на порог.
- Для дальних колец дешевле генерировать LOD напрямую из terrain_generator в грубой сетке (heightmap-семплирование), чем генерировать полный LOD0 и сворачивать. Это отдельная задача: `terrain_generator::generate_lod(column, scale)`.

### 4.3 Бесшовные стыки — юбки (skirts)

На границе колец соседние чанки имеют разный масштаб — по шву видны щели (грань LOD0 не совпадает с гранью LOD1). Для кубических вокселей решение — юбка: по периметру чанка каждый граничный квад дополнительно вытягивается вниз/вбок на `voxel_scale` родного масштаба, закрывая возможную щель. Реализация — в `emit_rect`: для квадов на границе модели добавляется второй квад, перпендикулярный основному, высотой в один воксель, направленный «внутрь земли». Перекрытие геометрии на швах невидимо (z-fight отсутствует, юбка утоплена), стоимость — единицы процентов вершин. Это сильно проще Transvoxel и в кубической эстетике артефактов не даёт.

### 4.4 Управление кольцами в world_grid

`world_grid_system::rebuild_active_set` вместо единого радиуса считает кольцо для каждой активной колонки. Смена кольца у колонки = запрос регенерации в новом масштабе с приоритетом ниже, чем загрузка новых колонок кольца 0; пока новый LOD не готов, рисуется старый (никаких «дыр» при переходах). Гистерезис из E2 применяется к границам колец так же, как к границе выгрузки.

```cpp
struct column_state {
    uint32 current_ring;   // что сейчас загружено
    uint32 target_ring;    // что требуется по расстоянию
    // переход current -> target через приоритетную очередь E2
};
```

### 4.5 Память

Чанки колец 1+ после мешинга могут освобождать воксельные данные (страницы), оставляя только меш + AABB: воксели дальних колец нужны заново только при смене кольца, а это регенерация. Флаг `discard_voxels_after_mesh` на колонку. Это снижает потребление page_pool в разы.

## Интеграция

- `world_grid` / `world_grid_system` — кольца, состояния колонок, приоритеты регенерации.
- `terrain_generator` — интерфейс генерации в масштабе.
- `mesh.inl.h::emit_rect` — юбки (по флагу «квад на границе модели»).
- `chunk` — чанки разных масштабов уже поддерживаются через `voxel_scale`; проверить `world_to_chunk_coord` на кольцах.
- Каллинг: AABB чанков уже per-instance в cull.comp — работает без изменений.

## Приёмка

- Дальность 32+ колонки (2+ км) при бюджете памяти ≤ 2 ГБ VRAM и стабильных 60 FPS на целевой GTX 1650 (цель из PRD).
- Переход игрока между кольцами не вызывает видимых дыр или «морфинга» дольше 1 с.
- Скриншот-тест швов: на стыках колец нет просветов при любом ракурсе камеры.

## Задачи эпика

1. Кольца и состояния колонок в world_grid_system (+ гистерезис).
2. downsample_2x (скалярный) + быстрый путь по uniform-страницам.
3. Юбки в emit_rect + скриншот-тесты швов.
4. generate_lod в terrain_generator для дальних колец.
5. Сброс воксельных данных после мешинга для колец 1+.
6. (После E1) битовый даунсэмплинг через occupancy.

# E5. Журнал правок, версии чанков и wire-формат

## Проблема

Сетевой код и сохранения требуют одного и того же фундамента, которого сейчас нет: способа компактно описать «чем мир отличается от процедурного базиса» и способа быстро ответить «одинаков ли чанк у нас с тобой». Если строить сохранения без этого (полные дампы чанков), сеть потом потребует переделки; если заложить журнал сейчас — сохранения и сеть станут одним механизмом.

Ключевое требование к генератору: **детерминизм**. Один seed должен давать бит-в-бит одинаковый мир на всех машинах. Проверить: нет зависимости от порядка обхода unordered-контейнеров, нет неинициализированной памяти, float-математика шума одинакова (компилировать генератор с выключенным fast-math; либо перейти на fixed-point шум).

## Целевой дизайн

### 5.1 Модель данных

```cpp
// engine/include/vw/world_state/edit_journal.h
namespace vw::ws {

struct voxel_edit {
    vec3i   pos;        // мировые координаты
    block_id new_id;
    uint8   channel;    // material / state (E3)
    uint8   value;      // для channel != material
    uint32  chunk_version;  // версия чанка ПОСЛЕ применения этой правки
    uint64  tick;       // серверный/хостовый тик
    uint32  author;     // player id
};

struct chunk_meta {
    uint32 version   = 0;   // счётчик применённых правок
    uint64 base_hash = 0;   // хэш процедурного базиса (кэш, для самопроверки)
    uint64 hash      = 0;   // xxhash64 текущего содержимого (лениво)
    bool   dirty     = true;
};

}  // namespace vw::ws
```

Правила:

- `set_voxel` в геймплее идёт только через журнал: `journal.apply(edit)` → инкремент `chunk_meta.version` → фактическая запись в `model` → пометка dirty для хэша и ремеша. Прямой `model::set_voxel` остаётся для генерации и инструментов.
- Журнал персистентен: append-only лог на диске + периодическая компакция (для каждого вокселя остаётся последняя правка). Сохранение мира = seed + компактированный журнал + метаданные. Это же — формат синхронизации при подключении.
- Undo/Redo Sculptor-а (command-паттерн, `base_operation`) не смешивается с журналом мира — это разные системы (редактор моделей vs мировое состояние).

### 5.2 Синхронизация состояний

Подключение клиента к хосту:

1. Клиент сообщает seed-версию и список `{chunk_coord, version}` для чанков в его интересе (или ничего, если мир новый).
2. Хост сравнивает версии: совпадает — чанк актуален; отстаёт — досылается хвост журнала по этому чанку; версия неизвестна клиенту — чанк генерируется у клиента из seed и доводится правками.
3. Самопроверка: раз в N секунд клиент шлёт `{coord, hash}` случайного подмножества чанков; расхождение → полная пересылка чанка (и лог для отладки — расхождение означает баг детерминизма).

В процессе игры: правки бродкастятся немедленно (`voxel_edit` — 24–32 байта), применяются идемпотентно по `chunk_version` (правка с версией ≤ текущей отбрасывается). Разрешение конфликтов — last-writer-wins по `(tick, author)`; для песочницы этого достаточно.

### 5.3 Wire/дисковый формат чанка (полная пересылка)

Для случаев «версия разошлась безнадёжно» и для регионального кэша на диске — компактный формат, использующий страничную структуру:

```text
chunk_blob:
  header: coord, version, channel_mask
  для каждого канала:
    palette: uint16 count, block_id[count]        // локальная палитра чанка
    pages:   512 × page_desc
      page_desc: mode(2 бита) | payload
        empty:   ничего
        uniform: palette_idx (обычно 1 байт)
        sparse:  512 × palette_idx, битпак по ширине палитры (1–9 бит),
                 затем RLE по рану
  всё сжимается zstd (level 3 онлайн / 19 для диска)
```

Ожидаемые размеры: равнинный чанк 64³ — сотни байт; сложный пещерный — единицы–десятки КБ. Локальная палитра чанка почти всегда ≤ 16 материалов → 4 бита на воксель до RLE.

### 5.4 Interest management

Зона интереса игрока = его кольцо 0 (+1 колонка гистерезиса). Хост ведёт по каждому игроку множество колонок интереса; правки бродкастятся только подписчикам колонки. Механика идентична `world_grid_system::rebuild_active_set` — вынести общий код в переиспользуемый компонент (это уже сделает будущий сервер тонким).

### 5.5 Про «p2p mmo» — архитектурная рекомендация

PRD фиксирует ко-оп до 8 игроков — это правильный масштаб. Рекомендуемая модель — **host-authoritative**: хост владеет истиной (журнал, тики, NPC), клиенты шлют интенты. Плюсы: единственная точка разрешения конфликтов, простая консистентность, работает offline (хост = одиночная игра). Чистый p2p с распределённой авторитетностью не даёт ни анти-чита, ни простой консистентности, и его миграция хоста — отдельный многомесячный проект. Важно: весь дизайн E5 (журнал, версии, интерес) не зависит от выбора — он одинаково служит host-authoritative, выделенному серверу и региональным узлам, поэтому решение о топологии можно принять позже без переделок движка.

## Интеграция

- Новый модуль `engine/include/vw/world_state/` (журнал, меты, hash) — намеренно вне `gfx`, чтобы будущий headless-сервер линковал мир без рендера. Это стоит сделать частью эпика: сейчас chunk/world_grid живут в `vw::gfx` и тянут entity/ECS рендера — выделить чистое «мировое состояние» из графа зависимостей.
- `world_grid::set_voxel` — публичный путь через журнал.
- Сериализаторы vox/voxa — не трогаются (это формат моделей Sculptor); формат мира — новый.
- xxhash — маленькая вендорная зависимость (или собственный FNV-1a на старте).

## Приёмка

- Детерминизм: генерация мира на двух разных машинах (MSVC/Clang) даёт равные хэши всех чанков тестового региона.
- Цикл сохранение → загрузка восстанавливает мир бит-в-бит (сравнение хэшей).
- Символический сетевой тест (loopback, 2 процесса): 1000 правок/мин с двух сторон, расхождений хэшей нет, каждая правка ≤ 40 байт на проводе.

## Задачи эпика

1. Выделение world_state из vw::gfx (рефакторинг зависимостей chunk/world_grid).
2. Аудит детерминизма terrain_generator (+ фиксация флагов компиляции).
3. edit_journal + chunk_meta + путь set_voxel через журнал.
4. Персистентность журнала: append-log + компакция; сохранение = seed + журнал.
5. chunk_blob формат (палитра + битпак + RLE + zstd) + fuzz-тесты кодека.
6. Хэши чанков (лениво, в gen-потоках) + самопроверка.
7. Interest-компонент (переиспользование логики active set).

# E6. Occlusion culling: two-phase HZB + связность чанков

## Проблема

`shaders/cull.comp` выполняет только frustum-тест AABB. В воксельном мире с рельефом фрустум пропускает всё, что за холмом, а под поверхностью — все пещеры и подземелья: 50–90% рисуемых чанков не дают ни одного видимого пикселя. Две взаимодополняющие техники: HZB закрывает «за холмом», связность — «под землёй».

## 6.1 Two-phase HZB culling

### Схема кадра

```text
Фаза 1: рисуем чанки, видимые в ПРОШЛОМ кадре (список сохранён)
        → depth buffer почти полон
Построение HZB: mip-цепочка depth, каждый texel = max(4 родительских)
Фаза 2: compute-тест ВСЕХ чанков против HZB
        → прошедшие, но не нарисованные в фазе 1 — дорисовываются
        → полный список видимых сохраняется для следующего кадра
```

Метод (изначально из Assassin's Creed Unity / Aaltonen) устойчив к движению камеры: ошибка первой фазы исправляется второй в том же кадре, артефактов «мигающих» объектов нет.

### Построение HZB

```glsl
// shaders/hzb_build.comp — один диспатч на mip, или single-pass через SPD
#version 460 core
layout(local_size_x = 8, local_size_y = 8) in;
layout(set = 0, binding = 0) uniform sampler2D src_depth;   // mip N-1
layout(set = 0, binding = 1, r32f) writeonly uniform image2D dst; // mip N

void main() {
    ivec2 dst_px = ivec2(gl_GlobalInvocationID.xy);
    ivec2 src_px = dst_px * 2;
    vec4 d = vec4(
        texelFetch(src_depth, src_px, 0).r,
        texelFetch(src_depth, src_px + ivec2(1,0), 0).r,
        texelFetch(src_depth, src_px + ivec2(0,1), 0).r,
        texelFetch(src_depth, src_px + ivec2(1,1), 0).r);
    // reversed-Z: дальше = меньше; берём min как «самое дальнее» для консервативности
    imageStore(dst, dst_px, vec4(min(min(d.x,d.y), min(d.z,d.w))));
}
```

Рекомендация: перейти на reversed-Z (если ещё нет) одновременно с HZB — и точность депта на больших дистанциях (важно для E4-дали), и консервативный min-редьюс естественнее.

### Тест в cull.comp

```glsl
bool hzb_visible(vec3 bmin, vec3 bmax) {
    // 8 углов AABB -> clip -> экранный прямоугольник + ближайшая глубина
    vec2 rect_min = vec2(1.0), rect_max = vec2(0.0);
    float nearest = 0.0; // reversed-Z: ближе = больше
    for (int i = 0; i < 8; i++) {
        vec4 clip = view_proj * vec4(corner(bmin, bmax, i), 1.0);
        if (clip.w <= 0.0) return true;     // угол за камерой — консервативно видим
        vec3 ndc = clip.xyz / clip.w;
        rect_min = min(rect_min, ndc.xy * 0.5 + 0.5);
        rect_max = max(rect_max, ndc.xy * 0.5 + 0.5);
        nearest  = max(nearest, ndc.z);
    }
    vec2 size_px = (rect_max - rect_min) * viewport_size;
    float mip = ceil(log2(max(max(size_px.x, size_px.y), 1.0)));
    // 4 семпла углов прямоугольника на выбранном mip
    float far_depth = min4(
        textureLod(hzb, rect_min, mip).r,
        textureLod(hzb, vec2(rect_max.x, rect_min.y), mip).r,
        textureLod(hzb, vec2(rect_min.x, rect_max.y), mip).r,
        textureLod(hzb, rect_max, mip).r);
    return nearest >= far_depth;  // AABB не дальше самого дальнего в HZB
}
```

Интеграция в существующий пайплайн минимальна: `cull_pipeline` получает второй диспатч и биндинг HZB; `renderer` — сохранение списка видимых (буфер индексов чанков) между кадрами и второй indirect-проход. Каскады теней продолжают ходить по frustum-only пути (HZB строится от камеры).

## 6.2 Связность чанков (cave culling)

HZB не знает, что вход в пещеру, попавший в кадр, не ведёт к конкретному подземному чанку. Связность решает это топологически.

### Вычисление на чанк

При мешинге (E1: по occupancy это дёшево) флуд-филлом по пустым вокселям вычисляется, какие пары граней чанка соединены воздухом:

```cpp
// 6 граней -> C(6,2) = 15 пар -> uint16
auto compute_face_connectivity(const chunk_occupancy& occ) -> uint16 {
    uint16 bits = 0;
    // BFS от каждой пустой границы; посещённость — bitset 64³/8 = 32 КБ
    // (в storage потока, переиспользуется)
    // для каждой стартовой грани: множество достигнутых граней -> пары
    ...
    return bits;
}
```

Результат кладётся рядом с мешем (в компонент чанка). Пересчёт — только при ремеше.

### Обход на CPU

Каждый кадр (или при смене чанка камерой) — BFS по сетке загруженных чанков от чанка камеры:

```cpp
// упрощённо (советы Tommo/MC: направление входа ограничивает выход)
struct vis_node { vec3i coord; uint8 entered_face; };
// сосед посещается, если connectivity чанка соединяет entered_face
// с гранью выхода И выход не «разворачивается» против направления обзора
```

Выход BFS — битовый набор потенциально видимых чанков; он подмешивается в cull.comp третьим условием (буфер uint32 по индексам инстансов) либо фильтрует на CPU список кандидатов до диспатча. BFS по нескольким тысячам чанков — доли миллисекунды.

Эффект: стоя на поверхности, не рисуем ни одного подземного чанка; стоя в пещере — не рисуем поверхность, кроме видимой через вход.

## Приёмка

- Сцена «холмистый рельеф, камера у земли»: число нарисованных чанков падает ≥ 2× против frustum-only (метрика — счётчики из cull.comp, вывести в debug_window).
- Сцена «поверхность над системой пещер»: подземные чанки не рисуются (счётчик = 0).
- Нет визуальных пропаданий при резких поворотах камеры (two-phase корректность), тест — скриптованная камера + сравнение кадров с эталоном без каллинга.

## Задачи эпика

1. Reversed-Z (если нет) + HZB build pass.
2. Сохранение списка видимых, две фазы отрисовки в renderer.
3. hzb_visible в cull.comp + счётчики статистики.
4. compute_face_connectivity при мешинге (после E1 — по occupancy).
5. BFS видимости + подмешивание в каллинг.

# E7. Кэширование теневых каскадов и мелкие оптимизации рендера

## Проблема

`renderer_shadow.inl.h` рисует геометрию в 4 каскада каждый кадр — по сути, вся сцена растеризуется 5 раз. При статичном солнце и редких правках дальние каскады почти не меняются от кадра к кадру.

## Дизайн

### 7.1 Расписание обновления каскадов

- Каскад 0 (ближний) — каждый кадр.
- Каскад i — каждый 2^i кадр (1: через кадр, 2: раз в 4, 3: раз в 8), плюс форс-обновление при: правке мира в объёме каскада, телепорте камеры, изменении направления света больше порога.
- Матрицы дальних каскадов стабилизируются снэппингом к тексель-сетке (устранение shimmer при движении камеры) — если ещё не сделано, делается в этой же задаче.

```cpp
struct cascade_schedule {
    std::array<uint32, shadow_map::cascade_count> last_update_frame{};
    std::array<bool,   shadow_map::cascade_count> force_dirty{};

    auto needs_update(uint32 cascade, uint32 frame) const -> bool {
        if (force_dirty[cascade]) { return true; }
        const uint32 interval = 1u << cascade;
        return frame - last_update_frame[cascade] >= interval;
    }
};
```

`cull.comp` уже работает по проходам (`pass_count`, до 5 фрустумов) — пропуск каскада = исключение его фрустума из pass-набора кадра, счётчики и indirect-буферы это уже поддерживают.

### 7.2 Прочее (мелкие задачи, объединить в один спринт)

- **Шейдинг дальних LOD**: для колец 2+ (E4) — упрощённый fragment-путь: без PCF 3×3 (1 семпл или вообще без теней на последнем кольце), без rim light, без point lights. Реализация — вариант пайплайна или спец-константа; выбор по инстансу через LOD-кольцо в данных инстанса.
- **Point lights**: сейчас (renderer_point_lights) убедиться, что применяется отсечение по радиусу на CPU/GPU; при росте числа источников — кластеризация (Forward+) отдельным эпиком, пока не требуется.
- **Пирамида мипов депта** из E6 переиспользуется и для мягких контактных теней в перспективе — фиксируем как совместимость, не делаем сейчас.

## Приёмка

- GPU-время теневых проходов в статичной сцене падает ≥ 2.5× (профиль RGP/Nsight).
- Отсутствие видимых артефактов «запаздывающих теней» при беге и правках (форс-инвалидция срабатывает).

# E8. Устранение контеншена: page_pool и система задач

## Проблема

1. `page_pool` — один `std::mutex` на все alloc/free. Генерация колонок в нескольких потоках + мешинг + даунсэмплинг LOD (E4) будут сериализоваться на этом мьютексе (alloc идёт по одной странице при `promote_to_sparse`).
2. Отдельные потоки на подсистему (gen_threads_ в world_grid, поток в mesh_pool) не разделяют пул — при добавлении LOD и связности появится третья-четвёртая категория фоновых работ и ещё потоки.

## Дизайн

### 8.1 Локальные кэши страниц

```cpp
class page_pool_cache {
public:
    explicit page_pool_cache(page_pool& pool) : pool_(&pool) {}

    auto alloc() -> uint32 {
        if (local_.empty()) {
            local_ = pool_->alloc_batch(batch);   // 1 захват мьютекса на 32 страницы
        }
        const uint32 idx = local_.back();
        local_.pop_back();
        return idx;
    }

    void free(uint32 idx) {
        local_.push_back(idx);
        if (local_.size() >= batch * 2) {
            pool_->free_batch(std::span{local_}.subspan(batch));  // возврат излишка
            local_.resize(batch);
        }
    }

    ~page_pool_cache() { pool_->free_batch(local_); }

private:
    static constexpr uint32 batch = 32;
    page_pool* pool_;
    std::vector<uint32> local_;
};
```

`alloc_batch`/`free_batch` в пуле уже есть — кэш ложится поверх без изменения пула. Каждый воркер владеет своим кэшем (thread_local внутри функции потока или член контекста задачи).

### 8.2 Единый пул воркеров

Объединить gen-потоки world_grid и поток mesh_pool в один пул с типизированными задачами и приоритетами E2:

```cpp
enum class task_kind : uint8 { gen_column, mesh_chunk, downsample_lod, hash_chunk };

struct stream_task {
    task_kind kind;
    stream_priority priority;
    // payload по kind (variant или отдельные очереди на kind с общим пулом)
};
```

Число потоков = `hardware_concurrency() - 2` (кадр + ОС), настраиваемо. Это устраняет ситуацию «gen-потоки простаивают, mesh-поток захлебнулся» и даёт естественное место для задач E4/E5 (даунсэмплинг, хэши).

## Приёмка

- Профиль (Tracy/VTune) при агрессивном стриминге: время ожидания на мьютексе page_pool < 1% времени воркеров.
- Масштабирование: скорость генерации мира растёт ≥ 3× при переходе 1 → 6 воркеров.

# Карта зависимостей и рекомендуемый порядок

```text
E1 binary meshing ──────┬──> E4 LOD (битовый даунсэмплинг, юбки)
                        └──> E6 связность (по occupancy)
E2 бюджеты/transfer ────┬──> E4 LOD (очереди регенерации)
                        └──> E5 (интеграция правок без фризов)
E3 формат v2 ───────────┴──> E5 журнал (каналы в wire-формате)
E6 HZB — независим (кроме задачи 4)
E7 тени — независим
E8 контеншен — независим, но делать до E4 (LOD умножает фоновую работу)
```

Рекомендуемая последовательность спринтов:

1. **E1 + E8** — фундамент производительности CPU-стороны. Всё дальнейшее измеряется на их фоне.
2. **E2** — стабильный frametime и инфраструктура очередей для LOD.
3. **E3** — зафиксировать форматы до появления сохранений.
4. **E4** — даль обзора; самый большой и рискованный эпик, к нему подходить с готовыми E1/E2.
5. **E5** — журнал/версии/детерминизм; можно вести параллельно E4 (другие файлы).
6. **E6** — HZB, затем связность.
7. **E7** — в любой свободный слот.

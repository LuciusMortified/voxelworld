# Проверки качества

Компилятор ловит только то, что видно в одном юните трансляции и выражается в
типах. Всё остальное — выход за границу буфера, чтение освобождённой памяти,
гонка, знаковое переполнение, утечка — до́лжно ловить чем-то другим. Этот
документ описывает, чем именно, что из этого гоняется на каждый коммит и почему
остальное отложено.

## Что гоняется на каждый коммит

| Workflow | Джоб | Платформа | Что делает |
|---|---|---|---|
| CI | `build` (msvc/clang × Debug/Release) | Windows | полная сборка движка и приложений, `ctest` |
| CI | `headless` | Windows | ядро без GPU, **предупреждения — ошибки** |
| CI | `linux` | Linux, Clang + libc++ | полная сборка движка и приложений, `ctest` |
| CI | `lint` | Linux | `scripts/lint_modules.py` — гигиена интерфейсов модулей |
| Analysis | `sanitizers (address-undefined)` | Linux, Clang + libc++ | ASan + UBSan + LeakSanitizer по ядру |
| Analysis | `sanitizers (thread)` | Linux, Clang + libc++ | ThreadSanitizer по ядру |
| Analysis | `asan-windows` | Windows, MSVC | ASan по сборке, которой пользуются, включая мешер |
| Release | по тегам `v*` | Windows и Linux | сборка и упаковка `sculptor` |

Версия CMake прибита (`VW_CMAKE_VERSION`). Это не педантизм: `import std` открыт
экспериментальным гейтом, который принимает только точный UUID своей версии, и
раннер, обновившись сам, однажды уже уронил всю матрицу — молча, с жалобой на
отсутствие поддержки в тулчейне. Таблица UUID лежит в корневом `CMakeLists.txt`.

Чего это стоит по времени: сборки под Windows — от 4 до 10 минут каждая,
санитайзерные джобы — 3 минуты вместе со сборкой. Инструментация видна по самим
тестам: те же 222 теста идут 5 секунд обычной сборкой, 21 секунду под
ASan с UBSan и 35 секунд под TSan. Джоб `linux` — 5 минут: своего бинарного
кэша vcpkg под этот триплет не имеет и собирает `glfw3`, `imgui` и Catch2 из
исходников, но выходит всё равно быстрее любой сборки под Windows.

## Почему динамика живёт на Linux

На Windows из динамических проверок существует только ASan — ни UBSan, ни
LeakSanitizer, ни TSan там нет и не предвидится.

Выход дало то, что headless-половина движка (`vw.core`, `vw.ecs`, `vw.world`)
переносима: единственная платформенная строка на все три библиотеки — включение
ANSI-цвета в `log.cpp`. Clang с libc++ приносит собственный std-модуль, поэтому
на Linux `import std` работает штатным путём CMake, без `std.ixx`. Там и стоят
санитайзеры — ровно на той половине, где живут пулы потоков, арифметика с
индексами и разбор форматов, то есть всё, чем UB и утечки богаты. `vw.gfx` на CI
всё равно не исполняется: GPU у раннера нет.

Цена решения — `log.cpp` знает про libc++: базы часовых поясов
(`std::chrono::current_zone`) там до сих пор нет, и время в логе уходит в UTC.

## Полная сборка на Linux

Мешала ей не переносимость кода, а расхождение стандартных библиотек: `glfw3`,
`imgui` и Catch2 приезжают из vcpkg и собирались там системным gcc поверх
libstdc++, тогда как движок идёт на libc++. Чистый C пережил бы и смешение, а
Catch2 — нет: он несёт `std::string` через границу библиотеки. Насколько это не
теория, показал `asan-windows`: там та же рассинхронизация — предсобранный
Catch2 против инструментированных объектов — дала `LNK2038` про
`annotate_string`, и Catch2 пришлось собирать из исходников.

Лечит это overlay-триплет `x64-linux-libcxx` (`cmake/triplets/`): `-stdlib=libc++`
он передаёт портам через штатные `VCPKG_CXX_FLAGS`, а компилятор берётся из `CC`
и `CXX`. Компилятор именно оттуда, а не из своего тулчейн-файла: подсунуть его
можно только через `VCPKG_CHAINLOAD_TOOLCHAIN_FILE`, а тот замещает
`scripts/toolchains/linux.cmake` целиком — вместе с `-fPIC`, `CMAKE_SYSTEM_NAME`,
снятым `CMAKE_CROSSCOMPILING` и четырьмя policy, которые порты рассчитывают
получить. Имена компиляторов в CI с суффиксом версии, потому что другого
`llvm.sh` не заводит, а `clang++` из PATH на Ubuntu 24.04 — это Clang 18 с
libstdc++, то есть ровно то, от чего уходим.

Кода это стоило одной правки: `menu_bar.cpp` включал `<windows.h>` и
`<shellapi.h>` безусловно, хотя нужны они только ветке `ShellExecuteA`.
Остальная Windows-специфика вне ядра уже сидела под `#ifdef` и имела ветки для
macOS и POSIX. Молча деградирует единственное — замер памяти процесса в
`engine.cpp`: он считает через Psapi и на Linux возвращает ноль.

Чего эта сборка не доказывает: что `sculptor` на Linux **запускается**. GPU у
раннера нет, окно не открывается, слои валидации не отрабатывают. Джоб ловит
непереносимость на уровне компиляции и линковки — то есть тот её сорт, который
иначе копится молча и всплывает через полгода целым пластом.

## Каталог: чем вообще проверяют C++

Отметка в последнем столбце — состояние у нас.

### Динамические проверки

| Инструмент | Что ловит | Где работает | У нас |
|---|---|---|---|
| **AddressSanitizer** | выход за границы кучи, стека и глобалов, use-after-free, double-free | Clang, GCC, MSVC | да, Linux и Windows |
| **LeakSanitizer** | утечки памяти | Linux/macOS (в составе ASan) | да, Linux |
| **UndefinedBehaviorSanitizer** | знаковое переполнение, сдвиги, нулевые ссылки, кривые касты, невыравненный доступ, недопустимые значения `enum`/`bool` | Clang, GCC | да, Linux |
| **ThreadSanitizer** | гонки данных, взаимные блокировки | Clang, GCC | да, Linux |
| **MemorySanitizer** | чтение неинициализированной памяти | только Clang + инструментированная libc++ | нет, см. ниже |
| **Valgrind (memcheck)** | то же, что ASan+LSan, но без перекомпиляции | Linux | нет, перекрыт санитайзерами |
| **Dr. Memory** | Valgrind-подобное для Windows | Windows | нет |
| **CRT Debug Heap** | утечки и порча кучи в отладочной сборке MSVC | Windows | нет, перекрыт ASan |
| **Application Verifier** | ошибки работы с хендлами и кучей Windows | Windows | нет |
| **`/RTC1`** | неинициализированные локальные, порча стека | MSVC Debug | по умолчанию в Debug |
| **Отладочные итераторы** | выход за границы контейнеров, недействительные итераторы | `_ITERATOR_DEBUG_LEVEL` (MS STL), `_LIBCPP_HARDENING_MODE` (libc++), `_GLIBCXX_ASSERTIONS` | включены MS STL в Debug |
| **Fuzzing** (libFuzzer, AFL++) | падения и зависания на неожиданном вводе | Clang | нет, но есть очевидная цель — разбор `.vox`/`.voxa` |
| **Слои валидации Vulkan** | нарушение контрактов API, которых не видит компилятор | везде | локально, в CI нет GPU |

### Статический анализ

| Инструмент | Чем полезен | У нас |
|---|---|---|
| **Предупреждения компилятора** | самый дешёвый анализатор; `/W4 /permissive-`, `-Wall -Wextra -Wshadow` и родня | да, `cmake/vw_warnings.cmake` |

| **`scripts/lint_modules.py`** | свои правила: ни одного `#include` своего заголовка, Vulkan C API только на границах | да, джоб `lint` |

## Что сознательно не взяли

**MemorySanitizer** требует, чтобы вся стандартная библиотека была собрана с
инструментацией, иначе тонет в ложных срабатываниях. Для проекта на `import std`
это отдельная сборка libc++ в CI — цена выше пользы, пока UBSan и ASan не
исчерпаны.

**Valgrind** делает то же, что ASan с LeakSanitizer, только в десятки раз
медленнее. Смысл появится, если понадобится проверять бинарь, который нельзя
пересобрать.

**clang-tidy** упирается в модули: `compile_commands.json` от MSVC ссылается на
`.modmap`, которого clang-tidy не понимает, а на Clang-сборке ему нужны готовые
BMI. Задача решаемая, но это отдельный заход.

**clang-format в CI** пока невозможен как проверка: репозиторий не отформатирован
по собственному конфигу (в одном `light.cpp` десятки строк длиннее заявленных
100 символов). Сначала общее форматирование отдельным коммитом, потом джоб.

## Долги

- `vw.gfx` и приложения дают около 140 предупреждений на `/W4`; поэтому
  `VW_WARNINGS_AS_ERRORS` включён только в headless-джобе, где ядро чисто.
- Trailing return type не выправлен в файлах, которые не переписывались целиком.
- Fuzzing разборщиков `.vox`/`.voxa` — самая очевидная незакрытая площадь.
- Покрытие тестами не измеряется, поэтому неизвестно, какая часть ядра реально
  проходит под санитайзерами.
